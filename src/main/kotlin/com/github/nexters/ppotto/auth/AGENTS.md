# auth

Social login and service token authentication domain.

| Directory | Description |
|-----------|-------------|
| `domain/` | One type per file: provider, login commands (`Kakao` = app SDK access token, `KakaoWeb` = browser authorization code + redirect URI, `Apple`), `SocialProfile`, `AuthUser`, `PendingTerm`, signup transaction result (`AuthSignup`), `LoginResult`, `TokenPair`, AUTH error codes |
| `application/` | `AuthService` login / active-user revalidation / refresh / logout written as `val` plus guard clauses, and the user/terms integration ports (one interface per file; `port/OAuthClient.kt` also owns the shared `List<OAuthClient>.byProvider()` duplicate-provider check). Only the signup section is wrapped in a transaction via `signupTransaction` (`TransactionOperations`) injected with `@Qualifier(SIGNUP_TRANSACTION)` |
| `infrastructure/oauth/` | `KakaoOAuthApi`/`AppleOAuthApi` HTTP Service interfaces (`@GetExchange`/`@PostExchange`, full URL passed as a `URI` method parameter) plus Kakao verification and Apple identity token/code exchange/revoke adapters. `AppleJwkProvider` owns the JWKS fetch and the expiring public-key cache so `AppleOAuthClient` only consumes `publicKey(keyId)`. `KakaoOAuthClient` serves both app and web commands: for `KakaoWeb` it first exchanges the authorization code at `auth.kakao.token-uri` with the REST API key and client secret (`AUTH-008` on failure), then runs the same `app_id` and `user/me` validation as the app path |
| `infrastructure/integration/` | Adapters wiring user signup, active-status lookup, default board, terms, and session integration plus provider account revocation. The signup adapter forwards to `UserService` and creates the default board, and carries no `@Transactional` of its own: the boundary is `AuthService.signUp`'s `signupTransaction` |
| `infrastructure/token/` | HS256 access JWT issuance and verification (`JwtTokenProvider`, straight-line guards, each rejection logged with a `reason=` and never the token value) plus the opaque refresh token and its Redis rotation adapter |
| `infrastructure/security/` | `BearerTokenAuthenticationFilter` (Bearer authentication context assembly, UUID principal) and `AuthAuthenticationEntryPoint`, which writes the 401 `ApiResponse` envelope itself. The filter's servlet auto-registration is disabled, so it only runs inside the security chains declared in `config/AuthSecurityConfig.kt`, and public-path decisions use the single source `global.config.PublicPaths` |
| `infrastructure/Sha256.kt` | `internal fun String.sha256Hex()` (`java.util.HexFormat`). The only SHA-256 hex helper in the domain: the Apple nonce comparison and the Redis refresh-token key both use it |
| `presentation/AuthApi.kt` | `/auth/login` (app), `/auth/login/web` (browser), `/auth/refresh`, `/auth/logout` version 1 mapping and Swagger contract: declares only response codes, descriptions, and schemas — examples are injected by `AuthApiExamples` |
| `presentation/AuthController.kt` | Auth API implementation with request binding and required typed logout user injection |
| `presentation/AuthApiExamples.kt` | `ApiExampleProvider` implementation. Defines per-provider app login requests, the Kakao web login request, new-signup/re-login responses, and `AUTH-001`~`AUTH-008` failure examples as real DTO instances |
| `presentation/AuthApiResponses.kt` | Auth-local composed Swagger response annotations (`@SignupInvalidInputApiResponse`, `@LoginUnauthorizedApiResponse`, `@WebLoginUnauthorizedApiResponse`, `@InvalidRefreshTokenApiResponse`, `@ConsentRequiredApiResponse`). Each names the AUTH codes the endpoint can actually produce, so `AuthApi` never repeats a `Content`/`Schema` block |
| `presentation/dto/` | Swagger-described authentication request and response schemas, one type per file. `WebLoginRequest.toCommand` accepts only `KAKAO` today and rejects `APPLE` with `COMMON-001` until a Services ID based web flow exists |
| `config/` | Validated Kakao (`app-id` plus the web-only `client-id`, `client-secret`, `token-uri`), Apple, and JWT properties plus adapter/application bean wiring. `AuthHttpConfig` registers the OAuth HTTP Service proxies via `@ImportHttpServices(group = "oauth")`, and timeouts are applied by the `spring.http.serviceclient.oauth.*` properties. `AuthTransactionConfig` defines the signup-only `signupTransaction` bean (`TransactionOperations`, timeout `SIGNUP_TRANSACTION_TIMEOUT_SECONDS` = 5s). `AuthSecurityConfig` owns every Spring Security chain (prod swagger Basic chain, `@Profile("!test \| secured")` JWT Bearer API chain, `@Profile("test & !secured")` permit-all fallback chain) plus the disabled `FilterRegistrationBean`; it lives here rather than in `global` so `global` never imports an auth type. Keep one blank line between constructor property groups |

## Rules

- `config/AuthSecurityConfig.kt` declares three chains: the Swagger chain (`@Order(0)`, prod Basic), the stateless Bearer API chain (`@Order(100)`, `@Profile("!test | secured")`), and the test-only permit-all fallback chain (`@Profile("test & !secured")`) that still runs `BearerTokenAuthenticationFilter` explicitly via `addFilterBefore`. Keep Swagger Basic auth ahead of the API chain and the fallback chain last. CORS itself is `global/config/CorsConfig.kt`.
- The API chain and the permit-all fallback chain both match any request, so their profiles must stay mutually exclusive. `!test | secured` and `test & !secured` cover every profile combination exactly once: with `test` alone the fallback runs, with `test` plus `secured` the production API chain runs, and everywhere else (`prod`, no profile) only the API chain runs. If both are ever active, Spring Security aborts context refresh with `UnreachableFilterChainException`.
- **The `secured` profile exists only so a test can run the production API chain.** `AuthSecurityChainTest` activates `@ActiveProfiles("test", "secured")` and pins anonymous `GET /boards` → 401 `COMMON-004`, `POST /auth/login` → 400 (permitAll, never 401), anonymous `GET /terms` → 200, anonymous `GET /stickers/{id}` → 404 (optional auth, never 401), a valid Bearer on `GET /boards` → 200, and that exactly one `FilterRegistrationBean<BearerTokenAuthenticationFilter>` exists with `isEnabled == false`. Never set `secured` in a deployed environment: `prod` already activates the API chain through `!test`. It costs one extra Spring context, so keep every production-chain assertion in that one spec.
- 401/403 from the API chain use the same `ApiResponse` error envelope through `AuthAuthenticationEntryPoint`.
- The app's SDK-based `POST /auth/login` contract is frozen; web login lives on the separate `POST /auth/login/web` so browser changes never touch what the native apps send. Both resolve to the same `users(provider, provider_user_id)` row because the exchanged web token belongs to the same Kakao app.
- Never expose provider SDKs or HTTP response types to application/domain.
- Never reference user/terms/board repositories directly; use `application.port` only.
- New signup handles user creation, default board creation, and pending-terms lookup in one transaction. If an intermediate step fails, the users row is rolled back too, so no board-less ghost account is left behind.
- The Apple authorization code exchange failure check must throw inside `signupTransaction.execute`. Moving this exception outside or catching it inside commits a ghost Apple account, so the Apple exchange failure scenario in `AuthSignupRollbackIntegrationTest` pins this with the real transaction boundary.
- The signup transaction uses the dedicated bean from `AuthTransactionConfig`, not Spring's shared default `transactionTemplate`. Without a timeout, waits on the `uk_users_provider_uid` unique index and `pg_advisory_xact_lock` can hold connection-pool connections indefinitely. Injection is pinned with `@Qualifier(SIGNUP_TRANSACTION)` instead of relying on name-based fallback.
- `AuthUserPort.findOrCreate` creates the user and the default board, but the transaction boundary belongs to `AuthService.signUp` (`signupTransaction`), not to the adapter: infrastructure declares no `@Transactional`. Calling the port outside that transaction gives no user/board atomicity, so `AuthSignupBoardRollbackIntegrationTest` drives it through `signupTransaction.execute { ... }`.
- Provider HTTP calls and token issuance/Redis writes run outside the transaction. Never put `@Transactional` on `login` — it would pin a DB connection for the duration of the provider read timeout.
- Concurrent signups for the same social account are serialized by the `uk_users_provider_uid` partial unique index and `saveIfAbsent` followed by re-lookup. Exactly one request becomes the new signup and the default board is created exactly once.
- The user email follows the same first-authorization-only rule as the name. Apple omits the `email` claim on re-login, so `AppleIdentity.email`/`SocialProfile.email` are nullable, the client falls back to the `id_token` in the authorization code exchange response (accepted only when its `sub` matches the identity token's), `UserService` keeps the stored email when the command carries none, and only a new signup without an email fails with `AUTH-007`. Restoring a non-null email locks every returning Apple user out with `AUTH-001`, which is the regression `AppleOAuthClientTest`/`UserServiceTest` pin.
- The user name has no code-level default or fallback. Kakao requires the `profile_nickname` consent and rejects a missing nickname with `AUTH-005`; a Kakao login request carrying `name` is rejected at the DTO (`COMMON-001`). Apple delivers the name only on the first authorization, so the login request's `name` is optional at the DTO, `UserService.findOrCreate` skips creation when it is absent, and `AuthService` converts that null into `AUTH-006` inside `signupTransaction`. Existing-user re-login without `name` keeps the stored name.
- The provider enums shared between auth and user, and the response DTOs shared between auth and terms, are converted explicitly in adapters.
- Refresh token reissuance revalidates the active user through the user application service before token issue/rotation.
- Plaintext provider refresh tokens travel only as far as the user port boundary; the user persistence adapter encrypts them immediately.
- Refresh tokens are never stored raw in Redis keys/values; they are identified only by SHA-256 hash.
- OAuth HTTP calls must apply `spring.http.serviceclient.oauth.connect-timeout/read-timeout` (`OAUTH_CONNECT_TIMEOUT_MILLIS`/`OAUTH_READ_TIMEOUT_MILLIS`; unit-less integers are milliseconds).
- `KAKAO_*_URI`/`APPLE_*_URI` are full-URL contracts including the path. Do not split them into base-url plus path; pass them as-is through the HTTP Service interface methods' `URI` parameter.
- HTTP Service interface return types stay nullable. Declaring them non-null turns a 2xx empty body into an NPE instead of a `RestClientException`, escaping the `AUTH-001` conversion path.
- `BearerTokenAuthenticationFilter`'s `try` covers token verification only. Wrapping `filterChain.doFilter` in it makes every `UnauthorizedException` thrown downstream in MVC clear the SecurityContext and come back relabelled as `COMMON-004`, which no controller test catches. `BearerTokenAuthenticationFilterTest` pins the propagation.
- Authentication failures are logged as a `reason=` at the point of failure (`JwtTokenProvider.verifyAccessToken`, `AppleOAuthClient.failAuthentication`, `AuthService.failRefresh`) and never carry the token or the `Authorization` header value. The client-facing code stays `COMMON-004`/`AUTH-002`, so the reasons live only in the log.
- `AppleOAuthClient.revoke` swallows `HttpClientErrorException` only. A 4xx means the token is already revoked, so withdrawal continues; a 5xx is Apple being down and must propagate so withdrawal aborts instead of hard-deleting our side while the provider account survives. `AppleOAuthClientTest` pins both directions (`shouldNotThrowAny` on 400, `shouldThrow<RestClientException>` on 500) — do not widen the catch to `RestClientException`.
- `AppleJwkProvider` takes its cache lifetime from `auth.apple.jwks-cache-seconds` (`AppleAuthProperties.jwksCacheSeconds`), so a test picks a TTL by passing its own properties — no separate constructor parameter. The TTL only decides whether a **cache hit** is reused: a `kid` that is not in the cached key set always refetches the JWKS, whatever the TTL. That is what makes an Apple key rotation work without a restart, so do not "fix" it by returning null on a miss. `AppleOAuthClientTest` pins both halves by counting `/keys` requests (same `kid` twice → one fetch at the default TTL, two at TTL 0; rotated `kid` → refetch and success).
- `KakaoOAuthApi`/`AppleOAuthApi` and their response DTOs are `internal`, so `KakaoOAuthClient`/`AppleOAuthClient`/`AppleJwkProvider` must stay `internal` too — a public class cannot expose an internal constructor parameter type. The test source set is associated with main, so tests still see them.
- `AuthUser.userId`/`PendingTerm.id` and every port signature use typed ids (`UserId`/`TermId`). The JWT subject string and Redis key/value strings are external representations converted inside `JwtTokenProvider`/`RedisRefreshTokenStore`; the SecurityContext principal stays a raw `UUID` (`verifyAccessToken(...).value` in `BearerTokenAuthenticationFilter`) and `CurrentUserArgumentResolver` resolves it into the handler parameter — typed `UserId` parameters compile down to the underlying `UUID`, so controller signatures are typed with no wrapping code.

### Do not add this again

- `AuthAccessDeniedHandler` was deleted on 2026-09-09. There is no method security, no granted authority, and CSRF is disabled, so Spring Security has no path that raises `AccessDeniedException`; the handler could only ever have been dead code. Reintroduce it only together with the authorization mechanism that actually throws.
- The `DEPLOY_ENV=dev` authentication-failure diagnostics (raw `Authorization` logging, `JwtAccessTokenVerificationException`, `JwtAccessTokenFailureReason`) were deleted on 2026-09-09 with the dev stack. They were dead in every deployed environment and logged bearer tokens in plaintext when enabled. Local debugging uses the `reason=` logs above.

Update this file when auth packages or contracts change.
