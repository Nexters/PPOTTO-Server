# sticker

Sticker and recap domain. A sticker is the aggregate root; recap photo links and `RecapComment` belong to one sticker.

| Directory | Description |
|-----------|---------|
| `domain/` | Pure Kotlin `Sticker` aggregate with statement-by-statement state transitions and validation, creation values, `RecapComment`, type, error code, and the sticker-image deletion event |
| `domain/Sticker.kt` | Aggregate root. `title` (title badge, max 15) and `summary` (recap one-line summary, max 100) are separate concepts checked by `isValidTitle` / `isValidSummary`. `mainColor` (hex, e.g. `#FF6B6B`) is the sticker's representative color used as the recap-detail screen background; `isValidMainColor` enforces `^#[0-9A-Fa-f]{6}$` as the final safety net after the analysis pipeline's own fallback. `MAX_ANALYSIS_STICKER_COUNT` (6) lives here so `STICKER-003` can interpolate it. `shareToken` / `sharePhotos` are carried but never transitioned in the domain — `RecapShareService` writes them through the command repository, the same shape as `viewedAt` and `imageKey` |
| `domain/RecapComment.kt` | Recap comment model, creation value, and `RecapCommentPosition` (id + posX/posY) update value. `posX`/`posY` must both be null or both set; that pair is the only thing distinguishing a floating speech bubble from a bottom keyword chip |
| `domain/StickerImageDeletionRequestedEvent.kt` | Sticker-image cleanup event and its `StickerImageDeletionReason`, published by `StickerCommandService` and consumed by `StickerImageCleanupEventListener` |
| `infrastructure/StickerRepository.kt` | jOOQ persistence for sticker roots, ownership validation, root lookups, share-token lookup (`findByShareToken`, which filters `deleted_at IS NULL` so a deleted recap's link dies with it), and board-scoped deletion targets including soft-deleted rows. The insert lists only the columns the application owns; layout columns come from their DB defaults (7.3) |
| `infrastructure/StickerCommandRepository.kt` | Field-specific atomic updates that never overwrite `deleted_at` from stale aggregate state, including `updateShare` / `clearShare`, plus withdrawal hard deletion by id |
| `infrastructure/StickerRecapRepository.kt` | jOOQ batch persistence and deletion for recap photo links and comments, plus per-id bulk position updates scoped to non-null `pos_x` rows |
| `infrastructure/BoardStickerAdapter.kt` | Board query/command port mappings backed by sticker application services. `StickerType` is translated to board's `BoardStickerType` with an exhaustive `when`, which is what keeps the type conversion honest: adding a sticker form breaks this file instead of silently reaching the board API as an undocumented value |
| `infrastructure/GcsStickerImageStorage.kt` | Read and deletion side of generated sticker images: production `StickerImageStoragePort` adapter delegating `stickers.image_key` read URL signing to the shared `global/storage/GcsReadUrlIssuer` and object deletion to `global/storage/ObjectStorageCleaner`. It does not upload — `analysis`'s `GcsStickerStorage` writes the object |
| `infrastructure/integration/WithdrawnUserStickerDeletionAdapter.kt` | User-domain `WithdrawnUserStickerDeletionPort` adapter through `StickerWithdrawalService` |
| `application/` | Transactional analysis-result save plus sticker query, command, regeneration, withdrawal, and async sticker-image cleanup pipelines |
| `application/StickerAccessService.kt` | Port-free sticker lookup shared by the query and command services. `getOwned` does root `findById` then a board-owner match through `BoardAccessService`, with both misses hidden as `STICKER-001`. It is the only ownership resolver — the recap-detail path uses it too, so a stranger gets `STICKER-001` instead of a filtered response |
| `application/RecapShareService.kt` | Recap share token issuing and revocation, split out from `StickerCommandService` to stay under the class function-count lint limit. `share` resolves ownership through `StickerAccessService.getOwned`, **reuses an existing `share_token`** and only updates `share_photos` so links already sent stay alive, and mints a fresh `UUID.randomUUID()` token otherwise; `unshare` nulls the token, invalidating every outstanding link immediately. Both are single-row updates, so neither opens a transaction |
| `application/RecapCommentCommandService.kt` | Bulk recap comment position update, split out from `StickerCommandService` to stay under the class function-count lint limit. Validates distinct ids and finite coordinates, resolves ownership through `StickerAccessService.getOwned`, then delegates the write to `StickerRecapRepository.updatePositions` and rejects the whole batch with `STICKER-004` if the updated-row count is short (missing id, wrong sticker, or a keyword-chip id with no existing position) |
| `application/StickerImageCleanupEventListener.kt` | Async best-effort GCS cleanup for generated sticker images after regeneration replacement or DB-update failure; deletion failures are logged and do not alter the request result |
| `application/port/` | Cross-domain contracts for analysis/photo ownership, recap photo metadata and signed URLs, drawing deletion, and sticker regeneration |
| `application/port/SinglePort.kt` | `List<T>.singlePort(name)` — the one place that resolves a collected port list to its single adapter and fails fast when absent or duplicated |
| `presentation/StickerApi.kt` | Version 1 sticker and recap mapping and Swagger contract |
| `presentation/StickerController.kt` | Sticker API implementation with request binding and typed user injection: `@AuthenticatedUser` on every endpoint except `getSharedRecap`, which takes no user at all and is addressed by share token instead of sticker id |
| `presentation/StickerApiExamples.kt` | `ApiExampleProvider` implementation. Defines the recap detail (one-line summary, 3 speech bubbles, 9 keyword chips), title update, comment position update request/response, and the `STICKER-001`, `STICKER-002`, `STICKER-004`, `STICKER-005`, `STICKER-006` failure examples as real DTO instances, plus the share request/response |
| `presentation/dto/` | Swagger-described sticker and recap request and response schemas. Every response type maps from its application result through a `from` companion with named arguments |
| `presentation/StickerApiResponses.kt` | Composed response annotations shared by the sticker endpoints: 404 `STICKER-001`, 400 `STICKER-004`, 400 `STICKER-005`/`STICKER-006`, and 409 `STICKER-002` |

## Rules

- Typed identifiers (`StickerId`, `AnalysisId`, `BoardId`, `PhotoId`, `UserId` from `global/identifier/`) flow end to end: domain models, repository public signatures, application services, the `application/port/` contracts, and presentation (`@AuthenticatedUser`/`@PathVariable` parameters and DTO id fields; JSON stays unwrapped uuid strings). jOOQ id columns are generated typed (codegen `forcedType`), so DSL bindings and `toDomain` pass typed ids straight through; raw `UUID` survives only in the advisory-lock bind and on `RecapComment.id` — a child-row id that never crosses a query boundary as a lookup key, so it stays raw by the `global/identifier/` rule.
- Exception grades follow origin, not shape. `Sticker`'s constructor and `regenerateSticker` validate a persisted DB row and adapter/LLM output, so they use `require` and a violation surfaces as a 500 bug. Client-originated values keep 4xx: `StickerCreation`, `RecapCommentCreation`, and `Sticker.rename` (reached from the title and layout commands) throw `InvalidInputException`. Never make the two share a throwing validator — the `isValid*` / `hasContent` predicates on `Sticker` are the shared part, and each caller picks its own grade.
- Business rejections carry a `StickerErrorCode`, never a bare `InvalidInputException(message = ...)`: `STICKER-003` analysis sticker count, `STICKER-004` uneditable recap comment, `STICKER-005` non-image regeneration, `STICKER-006` missing regeneration photos, `STICKER-007` undeletable sticker, `STICKER-008` uneditable sticker. Codes are never reused; a retired number stays a gap.
- `AnalysisResultSaveService.save` serializes on `@AdvisoryLock(namespace = "analysis-result", key = "#command.analysisId")` next to `@Transactional` (`global/lock/`). The aspect is ordered inside the transaction advice and `check`s an active transaction, so the lock can never be taken under autocommit and released immediately.
- **The lock is now taken before `validateOwnership`, where it used to follow it.** That is deliberate and safe: ownership validation is read-only, so ordering it after the lock changes no writes and no error code — a non-owner still gets `STICKER-001`. It only means a rejected caller waits behind a concurrent save of the same analysis, which is bounded by that save's transaction.
- The `analysis-result` namespace makes the lock key `analysis-result:{analysisId}`, where the old repository method hashed the bare `analysisId`. Nothing else ever locked that bare uuid, so no other caller can collide; the namespace is what keeps it that way as more locks are added.
- The SpEL key `#command.analysisId` reads a value-class property. Kotlin mangles the getter for a `value class`-typed property, so SpEL falls through to the backing field, which stores the unwrapped `UUID` — the key is the plain uuid string. `AnalysisResultSaveServiceTest`'s concurrent-save case is what proves the key still resolves and still serializes.
- Every collected port list is resolved through `application/port/SinglePort.kt`'s `singlePort(name)`. Do not re-implement `singleOrNull() ?: error(...)` inline — one helper keeps the failure message and the fail-fast timing identical everywhere.
- `Sticker` is soft-deleted through `stickers.deleted_at`.
- A recap has exactly one one-line summary and it lives on `stickers.summary`, not in `recap_comments`. It is LLM-written only — no API updates it, so `Sticker.summary` is a read-only `val` while `title` stays mutable through `rename`. `GET /stickers/{id}` returns it as the top-level `summary` field, outside the `sticker` object, because the board sticker list has no use for it.
- `recap_comments` has no type column. The two kinds are told apart by coordinates alone: `pos_x`/`pos_y` set means a speech bubble floating around the sticker, both null means a bottom `테마 분석` keyword chip. `chk_recap_comment_position` enforces that the pair is all-or-nothing and `RecapCommentCreation` rejects a half-filled pair before any write. Never reintroduce a boolean flag for this — it duplicates the coordinates and lets the two disagree.
- Recap responses carry every photo with no pagination. Clients derive the displayed photo count from the array length, so no count field is stored or returned.
- `sticker_photos` and `recap_comments` intentionally have no `deleted_at` in the final ERD. Deleting a sticker hard-deletes these child rows in the same transaction so recap content is no longer retained as active application data.
- Deleting stickers also removes `STICKER`-scoped drawings through exactly one `StickerDrawingCommandPort` adapter in the same transaction. Absence or duplication fails before any sticker mutation; the drawing owner provides the production adapter.
- Sticker code never accesses the analysis, photo, or board repositories directly. Board ownership is checked through the port-free `BoardAccessService`; analysis/photo ownership and recap photo metadata come through the application ports, whose adapters call the `analysis` application services. Per-sticker ownership resolution lives only in `StickerAccessService` (`getOwned` / `getWithOwnership`) so the 404-hiding policy cannot drift between services.
- `AnalysisPhotoOwnershipPort` must have exactly one adapter before analysis-result saving is enabled. The adapter must match `userId`, `boardId`, `analysisId`, and every source/recap photo id as an upload-completed photo; absence, duplication, or mismatch fails before the first sticker write. The production adapter is `analysis`'s `StickerAnalysisPhotoOwnershipAdapter`, backed by `AnalysisQueryService.ownsAnalysisPhotos`.
- An analysis owns at most six stickers for its lifetime, including soft-deleted stickers. Repeating or concurrently retrying analysis-result saving keeps and returns the first committed result instead of appending another result. The count rule itself is request shape, so it lives in `SaveAnalysisResultCommand.init` (`STICKER-003`) and rejects an over-long result before the service or the lock is reached; `Sticker.MAX_ANALYSIS_STICKER_COUNT` stays the one place the number lives.
- `StickerCommandService.regenerate` holds the DB-row regeneration claim through a private `withRegenerationLock(stickerId) { ... }` higher-order function, which throws `STICKER-002` when the claim fails and releases in a `finally`. It is one call site, so it is a function rather than an aspect. The use case then reads as load → validate → lock { port → swap → publish old-image deletion } with no lock bookkeeping in the body.
- `RecapPhotoQueryPort`, `StickerRegenerationPort`, and `StickerImageStoragePort` are integration contracts with exactly one adapter each: `analysis`'s `StickerRecapPhotoAdapter` (through `PhotoQueryService`), `analysis`'s `AnalysisStickerRegenerationAdapter` (through `PhotoQueryService`, Gemini, and `StickerStorage`), and this domain's `GcsStickerImageStorage` (through `global/storage/`). `RecapPhotoQueryPort.getByIds` takes the sticker's `analysisId` and `boardId` so the photo lookup is scoped at the query level and can never resolve another analysis's photos, whatever ids a caller passes. The sticker application still fails fast if an adapter omits requested media, so a partial photo or image-URL result is a 500, never a silently short response.
- `StickerImageStoragePort` owns both read-URL issuing and object deletion because both target the same `stickers.image_key` objects and must stay on one adapter.
- Withdrawal deletion is the only path that hard-deletes stickers and ignores `deleted_at`; it deletes the sticker image objects first, then the recap children and sticker rows in one transaction. It runs before the analysis, photo, and board domains delete their rows because `stickers` has real foreign keys into all three.
- Every port here is collected as `List<Port>` and resolved with `singlePort(...)`, so tests must not register additional `@Primary` fakes for them — an extra bean is a duplicate, not an override, and it breaks the context instead of replacing the adapter. Integration tests exercise the production adapters directly.
- All recap media URLs are read-only V4 signed URLs that expire after `gcs.read-signed-url-expiration-minutes` (1 hour per the client contract), so clients re-fetch instead of caching them.
- `StickerQueryService` stays non-transactional on purpose: read URLs are signed locally (CPU-bound RSA) after the repository reads return, so no query path may pin a DB connection through signing. Keep new read paths on the same shape — fetch rows first, sign outside any transaction.
- Sticker image objects are written by `analysis` and read here; the two never overlap. `analysis`'s `GcsStickerStorage` uploads the PNG and `analysis`'s `StickerObjectKeys` owns the key convention: initial analysis output is `stickers/{analysisId}/{themeIndex}-{sourcePhotoId}.png`, and recap regeneration output is `stickers/{stickerId}/{sourcePhotoId}-{regenerationId}.png`. This domain only signs GET URLs for the stored key. `stickers.image_key` must therefore hold the bare object key, never a `gs://{bucket}/...` URI — `GcsReadUrlIssuer` passes the stored value straight to `BlobId.of(bucket, key)`, so a `gs://` prefix would be signed as part of the object name and yield a URL that 404s.
- `POST /stickers/{stickerId}/regenerate` is a sticker command use case: sticker owns the API, ownership check, type/photo-composition validation, DB image-key swap, and cleanup event publication. The analysis domain owns the production regeneration adapter because it owns completed photo refs, Gemini source/subject selection, source-photo cutout, storage upload, and `StickerObjectKeys`. `stickers.main_color` is part of that same swap — `Sticker.regenerateSticker(sourcePhotoId, imageKey, mainColor)` and `StickerCommandRepository.updateStickerImage` both take the new color from `StickerRegenerationResult`, so a regenerated sticker's background color always matches its new image, not the one from initial analysis.
- Regenerated sticker images are temporary until `stickers.image_key` is updated in PostgreSQL. After a successful update, the previous image key is published for async best-effort deletion; if the DB update fails after upload, the newly generated image key is published for async best-effort cleanup and the previous key remains untouched. A future orphan cleanup batch is still the final safety net for missed GCS deletes.
- Controllers receive the authenticated `UserId` through `@AuthenticatedUser`; the shared resolver returns `COMMON-004` before controller execution when it is absent. **Every sticker endpoint including `GET /stickers/{stickerId}` requires authentication and resolves ownership through `getOwned`**, so a stranger gets `STICKER-001` rather than a filtered response.
- `GET /stickers/shared/{shareToken}` is the one anonymous path (`PublicPaths.OPTIONAL_AUTH_GET_PATTERNS`). It resolves the sticker by `stickers.share_token`, so an unshared, revoked, or soft-deleted recap is indistinguishable from a wrong token — all `STICKER-001`. It takes no user at all, which is why `isNew` is always `false` there: `viewedAt` is the owner's read state and `POST /stickers/{stickerId}/view` stays owner-only.
- **Photo exposure on the shared path is decided in exactly one place**: `StickerQueryService.buildRecap(sticker, isOwner, includePhotos)`. With `includePhotos = false` the recap photo ids are never read and `RecapPhotoQueryPort` is never called, so no GCS signed URL is minted at all — the shared link cannot leak originals even if a client asks for them. The owner path always passes `includePhotos = true`; the shared path passes `sticker.sharePhotos`. Never re-add a per-field filter on top of an already-issued URL list; withholding the URL is the control.
- `StickerRecapResult.share` (`RecapShareResult(photos)`) is present **only for the owner of a currently shared recap** — `null` covers both "never shared / revoked" and "not my recap", and the JSON omits the key entirely. Do not flatten it into an `isShared` boolean plus a meaningless `sharePhotos`: the nested nullable object is what makes "not shared but photos = true" unrepresentable. The client reads the key's presence as "currently shared" and seeds the share sheet's photo toggle from `share.photos`, so re-sharing cannot silently turn photos back on.
- The share token is a bare `UUID.randomUUID()` string with a unique index and no expiry. Expiry is deliberately absent — the owner revoking is the only way a link dies — while the photo URLs inside a response still expire on the usual `gcs.read-signed-url-expiration-minutes` clock, so a shared page re-fetches rather than caching.
- `getByBoardId`, `validateOwnedByBoard`, `updateLayouts`, and `deleteAllByBoardId` are the board-domain integration surface. The board domain validates board ownership before calling these board-scoped operations. `validateOwnedByBoard` only reports ownership as a `Boolean`; the board application decides the error, so `BoardStickerAdapter` never throws a board exception (1.3). `updateLayouts` does not re-run the count-based `validateOwnedByBoard` internally: every layout id must resolve in the `findAllByBoardId` active-sticker map (same `board_id` + `deleted_at IS NULL` predicate), so board-scope violations still fail with 400 `STICKER-008` without a second query.
- `StickerLayoutCommand` is `(id, StickerLayout)` — the layout values have exactly one shape from the board port through to the domain. Do not reintroduce a flattened per-field command; `BoardStickerLayoutCommand` (owned by board) is the only other layout shape and `BoardStickerAdapter` is the only place that maps it.
- `PATCH /stickers/{stickerId}/comments` (`RecapCommentCommandService.updatePositions`) is deliberately not part of the board layout surface above, even though both move `posX`/`posY`. Sticker layout coordinates are board-canvas-absolute and saved with drawings in one board-editing transaction (`PATCH /boards/{boardId}/layout`); comment coordinates are sticker-relative and edited from the recap detail screen only, so the board domain has no reason to know `RecapComment` exists. The endpoint only ever repositions comments that already carry a position — a keyword-chip id (originally null `pos_x`/`pos_y`) is rejected rather than promoted into a speech bubble, which `StickerRecapRepository.updatePositions`'s `POS_X IS NOT NULL` guard enforces at the SQL level so the service's row-count check catches it as a 400 without a separate lookup.
