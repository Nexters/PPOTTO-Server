# board

Board domain. `User : Board = 1:N`, and `Board : Drawing = 1:N`. Cross-domain referential integrity is enforced through application services and ports instead of direct repository access.

| Directory | Description |
|-----------|---------|
| `domain/Board.kt` | Pure Kotlin board model and board count/name policies |
| `domain/Drawing.kt` | Pure Kotlin drawing models as a sealed union: `Drawing.Stroke` (free-form `stroke` JSON plus `strokeWidth`) and `Drawing.Text` (`content`, `fontSize`, centre `posX`/`posY`, `maxWidth`, `rotation`), mirrored by `NewDrawing.Stroke`/`NewDrawing.Text` for creation. `NewDrawing`'s `init` is the single place every creation invariant lives — uuidv7 id, scope/`stickerId` agreement, non-blank colour, finite and positive geometry, and the 32-character text limit — and it raises `InvalidInputException(COMMON-001)` so a malformed request stays a 400. `Drawing.Text.MAX_CONTENT_LENGTH` is the one place that limit lives; the v2 request DTO's `@Size` reads it |
| `domain/DrawingType.kt` | Persisted discriminator for the drawing union: `STROKE` or `TEXT` |
| `domain/DrawingScope.kt` | Drawing ownership scope: `STICKER` or `BOARD` |
| `domain/BoardKind.kt` | `PERSONAL` or `SHARED`; `of(memberCount)` is the one place the rule "shared iff at least one `board_members` row" lives. Pure Kotlin; the named `BoardKind` OpenAPI component comes from `enumAsRef = true` on the `BoardSummaryV2Response.kind` property, so the domain carries no swagger import |
| `domain/BoardRole.kt` | The caller's role on a board: `OWNER` (`boards.user_id`) or `MEMBER` (`board_members`). Pure Kotlin; named `BoardRole` component via `enumAsRef = true` on `BoardSummaryV2Response.role` |
| `domain/BoardStickerType.kt` | Sticker form as this domain sees it: `IMAGE` or `TEXT`. Board owns the port contract, so it declares its own type instead of importing `sticker.domain.StickerType` — the adapter lives in sticker and referencing sticker types here would make board depend back on sticker and close the cycle. `BoardStickerAdapter` maps the two with an exhaustive `when`, so a new `StickerType` constant fails to compile until board decides how to expose it |
| `domain/BoardErrorCode.kt` | `BOARD-001` through `BOARD-005` API errors |
| `infrastructure/BoardRepository.kt` | Active-board CRUD, ownership filtering, owner-or-member read filtering (`findReadableById`, one file-level `ownedOrJoinedBy` condition shared with the list: `boards.id IN (member board ids UNION ALL owned board ids)`, written this way so each branch uses its own index — `ix_board_members_user` and `ix_board_user_created` — where `user_id = ? | `infrastructure/BoardWithdrawalRepository.kt` | Withdrawn-user board id lookup, hard deletion of the user's own `board_members` rows (boards they joined), and board hard deletion, kept out of `BoardRepository` so the active-board repository stays soft-delete only |
| `infrastructure/integration/StickerDrawingCommandAdapter.kt` | Sticker-domain `StickerDrawingCommandPort` adapter; soft-deletes sticker-scoped drawings through `DrawingRepository` inside the caller's transaction |
| `infrastructure/integration/WithdrawnUserBoardDeletionAdapter.kt` | User-domain `WithdrawnUserBoardDeletionPort` adapter through `BoardWithdrawalService` |
| `infrastructure/config/BoardExternalPortFallbackConfiguration.kt` | Fail-closed standalone fallbacks that back off when integration adapters are registered |
| `application/BoardCommandService.kt` | Default/create/rename/delete use cases and board policies as plain statements. Only `create` and `delete` open a transaction; `rename` is a single `UPDATE ... RETURNING` |
| `application/BoardAccessService.kt` | Port-free board existence, ownership, owner-or-member read access (`getReadableById`), and `MANDATORY`-propagation row-locking ownership lookup boundary for cross-domain services |
| `application/model/BoardLayoutUpdateCommand.kt` | Application-layer layout command model: changed sticker layouts, created `NewDrawing`s, and deleted drawing ids. Its `init` owns every duplicate-id rejection (`COMMON-001`), so an unbuildable layout never reaches the service |
| `application/model/BoardDetail.kt` | Application-layer board detail read model |
| `application/model/BoardSummary.kt` | Application-layer home-card read model for the v2 list, plus `MAX_PREVIEW_IMAGE_COUNT` (4), which board passes to the sticker summary port so the sticker domain never owns a home-UI number |

Memberships *of* the user are deleted explicitly; memberships *on* the user's boards go with the board through `fk_board_members_board ON DELETE CASCADE` |
| `application/BoardQueryService.kt` | Board list/detail composition through the sticker query port. `list` returns domain `Board`s (owned only, v1) and presentation maps them. `listSummaries` (v2) reads owned + joined boards in one query, then one batched `BoardStickerSummaryPort` call and one `BoardActiveAnalysisPort` call for the whole list (no per-board query), applies defaults for boards without stickers (0, empty previews, null colour, board `createdAt`), and sorts by `lastActivityAt` desc then id desc. ## Rules

- Typed identifiers (`BoardId`, `UserId`, `DrawingId`, `StickerId` from `global/identifier/`) flow end to end: domain models, repository public signatures, application services, the `application/port/` contracts, and presentation (`@AuthenticatedUser`/`@PathVariable` parameters and DTO id fields). jOOQ id columns are generated typed (codegen `forcedType`), so DSL bindings and `toDomain` pass typed ids straight through with no unwrapping; JSON stays unwrapped uuid strings via Jackson value class serialization, with `@get:JsonProperty` + `@get:Schema` pinning springdoc property naming on id fields.
- Same DB-generated column convention as `user/`: board `id`/`createdAt`/`updatedAt` come back via `RETURNING`, never set client-side.
- Drawing IDs are client-generated UUIDv7 values and are upserted for retry idempotency.
- Soft-deleted boards and drawings never appear in active queries.
- `user_id` has no FK constraint. Application services validate ownership.
- Board create, layout update, and delete acquire the same user-scoped transaction advisory lock before validation and mutation, declared as `@AdvisoryLock(namespace = BOARD_USER_LOCK_NAMESPACE, key = "#userId")` next to `@Transactional` (`global/lock/`). The key stays the literal `board-user:{userId}`; `BOARD_USER_LOCK_NAMESPACE` in `BoardCommandService.kt` is the one place that namespace lives, because two services share it. The aspect is ordered inside the transaction advice and `check`s an active transaction, so the annotation without `@Transactional` is a 500 rather than a lock that autocommit releases immediately.
- **`createDefault` carries its own `@AdvisoryLock` even though it only delegates to `create`.** Spring AOP proxies are per bean, so the internal `create(userId, null)` call is self-invocation and is not intercepted; without the annotation on the entry point the lock would silently never be taken. `auth`'s `AuthUserAdapter` calls `createDefault`, so it cannot be folded into a defaulted `create` parameter. Both annotations name the same key, so the nested call is a no-op re-entry rather than a second lock.
- `BoardRepositoryTest` proves the lock is real rather than a guard: it runs `boardCommandService.create` inside a `TransactionTemplate` and asserts a second JDBC connection is refused `pg_try_advisory_xact_lock` on the literal `board-user:{userId}` while that transaction runs, and granted once it ends. The concurrency specs (`BoardCommandConcurrencyTest`, `BoardLayoutConcurrencyTest`, `BoardAnalysisDeletionConcurrencyTest`) are the proof it still serializes.
- Board deletion checks the last-board rule first, then the active-analysis rule, so a single board reports `BOARD-004` even while an analysis is running. Ownership is resolved before both, so a non-owner always gets `BOARD-002`.
- Deletion and analysis creation serialize on the target board row (`findOwnedByIdForUpdate`), so an active analysis can never be attached to a board that is being deleted. Board deletion takes that row lock before the active-analysis rule, so an analysis that commits first is always observed.
- `BoardAccessService.getOwnedByIdForUpdate` is `@Transactional(propagation = MANDATORY)`: a caller without an open transaction fails fast instead of committing away the row lock right after taking it. It must never be `readOnly = true` because Postgres rejects `SELECT ... FOR UPDATE` in a read-only transaction.
- Single-statement reads and writes carry no `@Transactional`. `BoardAccessService.getById`/`getOwnedById`/`getReadableById`, `BoardQueryService.list`, `BoardWithdrawalService.findAllBoardIds`, and `BoardCommandService.rename` are one statement each, and `REQUIRED` propagation would open a real transaction for them. A transaction is opened only where several statements must commit together: `create`, `delete`, the layout update, and withdrawal deletion.
- Drawing creation invariants live in `NewDrawing.init`, not in the layout service. The layout request DTOs build `NewDrawing`s directly with the path `boardId`, so a malformed drawing is rejected before the service runs, and there is no parallel command union to keep in sync.
- Missing analysis or sticker integration adapters always fail closed, including empty sticker query, summary, and command requests, and `BoardExternalPortFallbackConfigurationTest` covers every fallback bean. The production context must resolve `BoardAnalysisActivityPort` and `BoardActiveAnalysisPort` to `BoardAnalysisActivityAdapter` and `BoardStickerSummaryPort` to `BoardStickerAdapter`, never to the fallback; `BoardStickerIntegrationTest` asserts exactly one bean of each.
- Drawing `scope=STICKER` requires `stickerId`; `scope=BOARD` forbids it.
- Layout request collections carry `@field:Valid` on the property, not `List<@Valid X>` on the element type. Kotlin emits the type-use form onto the constructor parameter, where Hibernate Validator never looks, so the per-drawing and per-sticker constraints silently never ran. `BoardLayoutControllerTest` pins both cascades through MockMvc: a non-`#RRGGBB` colour on the v2 drawing list and an over-length sticker title on the v1 and v2 sticker lists each return 400 `COMMON-001`.
- A drawing row is either a stroke or a text, and the DB enforces it: `chk_drawings_stroke_shape` and `chk_drawings_text_shape` tie each type to exactly the columns it must fill, the same way `chk_drawings_scope_sticker` ties scope to `sticker_id`. Adding a third type means a new check constraint, not a nullable column nobody validates.
- **A controller class carries exactly one type-level `@RequestMapping`.** Implementing two versioned API interfaces from one controller makes Spring apply one interface's version to every method and abort startup with `Ambiguous mapping`. One controller per API interface — that is why the detail and layout endpoints each have a v1 and a v2 controller.
- **`zIndex` moved from the `stroke` JSON into a real column, but the shipped v1 client still reads and writes it inside that JSON** (`board-drawing.ts` stuffs it there to share a stacking space with stickers). The v1 DTOs shim both directions through `DrawingLegacyZIndex.kt` and the JSON stored in the column never carries the key, so the two can never drift. v2 exposes `zIndex` directly. Deleting the shim breaks every deployed client.
- **The v1 detail response drops texts.** A v1 client parses `stroke.points` out of every drawing, so a text row would come back with no points and no `strokeWidth` and render as an empty path with a `NaN` hit radius. Texts are a v2-only feature, so v2 is where they appear.
- Colour format (`#RRGGBB`) is enforced on v2 requests only. v1 has always accepted any non-blank string and tightening it would reject requests the deployed client is entitled to make. `BoardLayoutControllerTest` guards that direction too: v1 `"FFD400"` must return 200 and store the string as sent, so adding `@Pattern` to the v1 DTO breaks a test instead of the deployed client.
- **Request-shape rejections live in the command types, business rejections in the service.** `BoardLayoutUpdateCommand.init` raises `COMMON-001` for duplicate created drawing ids, duplicate deleted ids, the same id in both lists, and duplicate sticker ids; `BoardStickerLayoutCommand.init` raises it for non-finite coordinates and `scale <= 0`. These need nothing but the request itself, so a malformed layout can never reach the service — the same reason `NewDrawing.init` owns drawing creation invariants. `BoardLayoutService` keeps only what needs other data: a created id that already belongs to another board and a deleted id that is not active on this board, both `BOARD-001`. `BoardLayoutServiceTest` asserts each reason, constructing the command inside `shouldThrow` for the ones the constructor now rejects.
- Cross-domain board ownership checks use `BoardAccessService`, which must stay independent of external ports.
- **v1 and v2 `GET /boards` answer different questions and must stay apart.** v1 is the board-picker dropdown (onboarding and board pages) and returns only boards the caller owns as `{id, name}`; v2 is the home-card list and returns owned + joined boards. Adding joined boards to v1 would put boards the caller cannot rename or delete into the picker of every deployed client.
- **`lastActivityAt` is when a sticker was last added, not when one was last touched.** It is the newest active sticker's `created_at`, falling back to the board's `created_at`. Recap views, share toggles, layout edits, and regeneration bump `stickers.updated_at` but must not reorder the home list, so `updated_at` is never the source here.
- **`analysisStatus` on a v2 card is the caller's own active analysis only.** `BoardActiveAnalysisPort.findByUserId` returns the one active analysis a user can have (`uk_analysis_active`), and only the card whose id matches shows it. Another member's analysis on a shared board never appears on my card. `BoardQueryServiceTest` covers both members' views.
- `listSummaries` is not wrapped in a transaction for the same reason as `getDetail`: the sticker summary port signs preview URLs after its reads. The board, sticker, and analysis reads are separate snapshots; a sticker added between them only shifts a count by one until the next fetch.
- **Board detail reads are owner-or-member; every write is owner-only.** `getDetail` (v1 and v2) resolves through `getReadableById`, so a participant can open a shared board from the list while a stranger still gets `BOARD-002`. Rename, delete, layout, and analysis creation keep `getOwnedById`/`getOwnedByIdForUpdate`, so a member's write is the same 404 a stranger gets. `BoardControllerTest` pins both directions. Widening a write path is T02/T03's decision, not a side effect of reusing `getReadableById`.
- Board code never reads analysis or sticker repositories directly.
- Withdrawal hard deletion is the only path that ignores `deleted_at`; every other query stays soft-delete aware. It runs after the sticker domain has removed its rows, because `stickers.board_id` is a real FK.
- `getDetail` must not be wrapped in `@Transactional`: the sticker query port signs V4 read URLs (local RSA, CPU-bound) and a surrounding transaction would pin a pooled connection through that work on the board-entry hot path. Read access still resolves first through `BoardAccessService.getReadableById` (owner or member), which is a single non-transactional `SELECT`, and READ_COMMITTED per-statement snapshots make a wrapping transaction add no consistency.

## 공동 보드 인계 메모 (T02 생성·이름변경·삭제, T03 초대·참여·나가기)

T01(보드 홈·목록)에서 정한 것과 남겨 둔 것이다. 남겨 둔 항목은 해당 티켓이 결정하고, 결정하면 이 절을 규칙으로 옮긴다.

**T01에서 정한 것**

- `board_members`에는 참여자만 담는다. 방장은 `boards.user_id`가 유일한 원천이고 방장 행은 넣지 않는다(백필도 없다). 방장 행을 넣으면 `BoardKind.of`가 개인 보드를 공동으로 판정하고 `participantCount`가 한 명씩 부풀어 오른다.
- 공동 보드는 참여 행이 하나 이상인 보드다(`BoardKind.of`). 마지막 참여자가 빠지면 별도 처리 없이 개인 보드로 돌아간다.
- `(board_id, user_id)`는 `uk_board_members_board_user`로 유니크다. 참여 API는 `ON CONFLICT DO NOTHING`으로 재시도 멱등을 얻으면 된다. 방장이 자기 보드에 참여하는 요청은 유니크로 막히지 않으므로 서비스에서 거부해야 한다.
- `user_id`는 `boards.user_id`처럼 FK가 없고, `board_id`는 `ON DELETE CASCADE` FK다. 보드 soft delete는 참여 행을 지우지 않는다. 목록과 상세가 `boards.deleted_at`으로 거르므로 보이지 않을 뿐이다.
- 읽기(`GET /boards` v2, `GET /boards/{boardId}` v1·v2)는 방장 또는 참여자, 쓰기는 전부 방장 전용이다. 참여 여부 판정은 `BoardRepository`의 `ownedOrJoinedBy` 한 곳뿐이고 "행이 있으면 참여 중"을 전제로 한다.
- 탈퇴 정리는 구현돼 있다. 탈퇴자의 참여 행은 `BoardWithdrawalRepository.hardDeleteMembershipsByUserId`가, 탈퇴자 보드에 달린 참여 행은 보드 하드 삭제의 CASCADE가 지운다.

**T03이 결정할 것**

- 나가기·내보내기·재참여 차단. 지금은 행 삭제 말고는 표현할 수단이 없어 내보낸 사용자를 다시 막을 수 없다. 상태 컬럼(`left_at`, `kicked_at` 등)을 추가하면 `ownedOrJoinedBy`와 `findAccessibleByUserId`의 참여자 수 서브쿼리를 같은 조건으로 함께 바꿔야 하고, 행이 수정되기 시작하므로 `updated_at`과 `set_updated_at` 트리거도 그때 추가한다.
- 참여자 쓰기 권한(레이아웃, 드로잉, 스티커 수정·삭제, 분석 생성). 지금은 모두 `getOwnedById`/`getOwnedByIdForUpdate`라 참여자는 `BOARD-002`를 받는다. 넓힐 때 주의할 점이 둘 있다. (1) 레이아웃 저장의 advisory lock 키가 `board-user:{userId}`라 서로 다른 사용자의 동시 저장은 직렬화되지 않는다. 공동 편집을 허용하면 보드 단위 키가 필요하다. (2) 보드 삭제의 진행 중 분석 검사 `hasActiveAnalysis(boardId, userId)`는 방장 본인의 분석만 본다. 참여자가 분석할 수 있게 되면 보드 기준으로 바꿔야 진행 중인 분석의 대상 보드가 지워지지 않는다.
- 참여자의 스티커 열람 상태. `isNew`/`viewed_at`은 스티커당 하나라 참여자가 상세를 열면 방장의 빨간 점이 그대로 보인다. 리캡 상세와 열람 처리(`GET /stickers/{id}`, `POST /stickers/{id}/view`)는 `StickerAccessService.getOwned` 기준이라 참여자에게 `STICKER-001`이다.
- 참여 인원 상한. 지금은 없다.
- 보드 100개 제한에 참여 보드를 셀지. `countByUserId`는 `boards.user_id`만 세므로 지금은 참여 보드가 제한과 마지막 보드 삭제 금지(`BOARD-004`) 계산 모두에서 빠진다.
- 초대 링크·코드와 참여 API 자체. 이 티켓에는 참여 행을 쓰는 운영 코드가 없고, 테스트는 `board/support/BoardTestFixtures.kt`의 `addBoardMember`로 행을 직접 넣는다.

**T02가 확인할 것**

- 새 보드는 참여 행 없이 생성되므로 항상 `PERSONAL`로 시작한다.
- 이름 변경과 삭제는 방장 전용을 유지한다. 공동 보드를 방장이 삭제하면 참여자 목록에서도 즉시 사라진다(soft delete 필터). 삭제 전에 참여자에게 알리는 정책이 필요하면 T02에서 정한다.
- v1 `GET /boards`(보드 선택 드롭다운)는 소유 보드만 준다. 드롭다운에 참여 보드를 넣으려면 v1을 바꾸지 말고 새 버전으로 내야 한다.
