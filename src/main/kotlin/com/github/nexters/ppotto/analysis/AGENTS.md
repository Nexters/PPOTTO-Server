# analysis

Analysis domain. Owns both `Analysis` and `Photo` — a photo only ever exists as part of an analysis (`Analysis : Photo = 1:N` via `photos.analysis_id`), so they share one domain package instead of being split into `analysis`/`photo`. No DB-level FK constraints (same reasoning as `board/`). The 90–100 photo count validation is implemented via service-level validation in `AnalysisService.createAnalysis` (returns 400 `ANALYSIS-001`). The one-active-analysis-per-user limit is enforced via service-level pre-check and a partial unique index `uk_analysis_active` on `analysis(user_id) WHERE status IN (UPLOADING, ANALYZING)` (returns 409 `ANALYSIS-002`). Daily quota is intentionally not implemented yet — see Rules below.

## Rules

- This tracks the client's real OpenAPI spec (`analysis` tag). Implemented: the 90–100 photo count check (`ANALYSIS-001`, service-level validation returning 400), the one-active-analysis-per-user limit (`ANALYSIS-002`, service pre-check + partial unique index `uk_analysis_active` returning 409 on violation), already-started/finished conflict (`ANALYSIS-003`, 409), active-analysis recovery, analysis status polling, and AI pipeline start from `start`. Not implemented yet: `DELETE /analysis/{id}`, `POST /analysis/{id}/reissue`, and the daily quota (out of scope for this PR — to be implemented later). Not-found cases use `NotFoundException(ANALYSIS-005)` for missing analysis and ownership mismatch in query APIs.
- Analysis creation and upload verification require the authenticated UUID principal. Foreign board and analysis identifiers return not found without exposing ownership.
- Board access goes through the port-free `BoardAccessService` only, never `BoardQueryService` or a board repository. `createAnalysis` takes the target board row lock (`getOwnedByIdForUpdate`) before the active-analysis pre-check, so it serializes against board deletion and a concurrent delete makes creation fail with `BOARD-002` instead of leaving an active analysis on a deleted board. That lookup is `MANDATORY`-propagation, so it may only be called from inside an already-open transaction.
- `AnalysisStatus.ACTIVE` (`UPLOADING`, `ANALYZING`) is the single definition of "in progress" shared by the active-analysis pre-check, active-analysis recovery, and the board deletion guard. Keep it aligned with the `uk_analysis_active` partial unique index predicate and the status transitions in `docs/api-spec/api-spec.md` and `docs/erd/schema.dbml`.
- Board deletion does not touch finished (`COMPLETED`/`FAILED`) analysis rows: the spec defines no deletion policy for analysis sessions, so the history stays and keeps pointing at the soft-deleted board.
- `startUpload` only accepts `UPLOADING` analysis. It checks photos currently `PENDING`; GCS objects with `size > 0` become `COMPLETED`, while missing or 0-byte objects become `FAILED` and are excluded from the pipeline. The analysis transitions to `ANALYZING`, so calling `startUpload` again returns `ANALYSIS-003` instead of acting as a no-op.
- `upload_status`/`status`/`content_type` are DB `VARCHAR`, not Postgres `ENUM`s — value-set validation lives only in the Kotlin enums; repositories map `String ↔ enum` at the boundary (`PhotoContentType.fromMimeType(...)` / `.mimeType`, same pattern as `UploadStatus.valueOf(...)` / `.name`).
- This domain owns the sticker domain's analysis/photo integration adapters (`infrastructure/integration/Sticker*`), following the same "provider side owns the adapter" rule as `BoardAnalysisActivityAdapter`. Sticker code never reads `analysis` or `photos` directly; every cross-domain read goes through `AnalysisQueryService` / `PhotoQueryService`.
- Ownership checks are fail-closed: a missing analysis, a user/board mismatch, or any photo id outside the analysis returns `false`, and the sticker domain converts that into `STICKER-001`.
- Recap photo reads require `photos.taken_at`; a null value is a data-integrity bug and fails with `IllegalStateException` (500) rather than being silently dropped.
- Any new test that invokes `AnalysisService` must `@Import` `analysis/support/AnalysisTestConfig` so the `@Primary` fake (`FakePhotoStorage`) replaces the real GCS adapter, same mechanism the former `image` domain used. Tests that only read (recap photo URLs) can use the real GCS adapter — V4 signing is local RSA against the dummy test key with no network call.
- Photo objects and generated sticker objects share one bucket but not one key space: `PhotoObjectKeys` owns `photos/{analysisId}/...` and `StickerObjectKeys` owns `stickers/{analysisId}/...`. Uploads (`GcsPhotoStorage`, `GcsStickerStorage`) live here; read URL signing for both is the shared `global/storage/GcsReadUrlIssuer`, reached through `PhotoStorage.issueReadUrls` for photos and through the sticker domain's `StickerImageStoragePort` for stickers.
- `AnalysisStickerResult.imageKey` must receive `StickerObjectKeys.keyFor(...)`, not a `gs://` URI — the latter would be signed as a literal object name and produce a broken read URL.
- `ThemeAnalysisResult.text` is the prompt's "1~2문장의 리캡 문구" and now fills `AnalysisStickerResult.summary` (the recap's `한 줄 요약`), not a recap comment. It used to be saved as the single non-floating comment, but that "하단 순차 노출 문장형" UI was removed. `comments` therefore stays empty until the prompt starts producing the speech-bubble and keyword-chip text; the sticker domain accepts an empty list. `Sticker.MAX_SUMMARY_LENGTH` is 100, well above what "1~2문장" yields, so keep the prompt's length wording in sync if either side changes.
- Withdrawn-user cleanup deletes GCS objects before rows, so a failure after object deletion leaves rows that the next batch run retries; deleting rows first would leak objects nothing can find again. It is the only path that hard-deletes analysis and photo rows.
- The old `images` table / `image` domain (file-name-based, per-image signed URL issuance and client-reported upload completion) was fully replaced by this domain in the same change — see git history if you need the old shape.
