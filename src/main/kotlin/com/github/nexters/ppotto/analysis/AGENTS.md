# analysis

Analysis domain. Owns both `Analysis` and `Photo` — a photo only ever exists as part of an analysis (`Analysis : Photo = 1:N` via `photos.analysis_id`), so they share one domain package instead of being split into `analysis`/`photo`. No DB-level FK constraints (same reasoning as `board/`). The 20–100 photo group count validation (each group 1–10 photos, `MIN_GROUP_COUNT`/`MAX_GROUP_COUNT`/`MAX_BURST_GROUP_SIZE`) is implemented in the `init` of `CreateAnalysisCommand` and `PhotoUploadGroupRequest` (returns 400 `ANALYSIS-001`/`ANALYSIS-010`/`ANALYSIS-009`), so an invalid request never reaches `AnalysisService`. The one-active-analysis-per-user limit is enforced via service-level pre-check and a partial unique index `uk_analysis_active` on `analysis(user_id) WHERE status IN (UPLOADING, ANALYZING)` (returns 409 `ANALYSIS-002`). The pre-check is deliberately kept on top of the constraint: it runs inside the board row lock that `createAnalysis` already holds, so the common case answers 409 without burning an insert and a rolled-back transaction, while the constraint stays as the race-proof fallback. Daily quota is intentionally not implemented yet — see Rules below.

| `application/AnalysisPipelineService.kt` | Vertex AI pipeline: classifies photos into themes, then processes each theme in virtual-thread tasks while preserving `themeIndex` result order. `run(pipelineRun, photos, onProgress)` takes the `PipelineRun` recorder the listener created, so every timing and log line lives in the recorder and no method body here holds `log.`, `System.nanoTime` or `runCatching`. ## Rules

- Typed identifiers (`AnalysisId`, `PhotoId`, `BoardId`, `UserId`) run end to end through this package: controller, DTOs, application services, `Analysis`/`Photo` models, the `PhotoStorage`/`ThemeClassifier` ports, the `integration/` adapters, and the public signatures of `AnalysisRepository`/`PhotoRepository`. jOOQ id columns are generated typed (codegen `forcedType`), so DSL bindings and `toDomain` take and return typed ids directly — there is no wrap/unwrap layer left in this domain. Raw `UUID` remains only where it is not an entity id: `photos.burst_group_id` (an internal grouping token that crosses no domain boundary) and the sticker regeneration id.
- This tracks the client's real OpenAPI spec (`analysis` tag). Implemented: the 20–100 photo group count check, each group 1–10 photos (`ANALYSIS-001`, enforced in `CreateAnalysisCommand.init`, returning 400), the one-active-analysis-per-user limit (`ANALYSIS-002`, service pre-check + partial unique index `uk_analysis_active` returning 409 on violation), already-started/finished conflict (`ANALYSIS-003`, 409), the `UPLOADING`-only cancel (`ANALYSIS-004`, 409, `DELETE /analysis/{id}`), active-analysis recovery, analysis status polling, upload URL reissue (`POST /analysis/{id}/reissue`), and AI pipeline start from `start`. Not implemented yet: the daily quota (out of scope for this PR — to be implemented later). Not-found cases use `NotFoundException(ANALYSIS-005)` for missing analysis and ownership mismatch in query APIs, including `cancelAnalysis` and `startUpload`/`reissueUploadUrls` (both share `findOwnedAnalysis`, which consistently throws `ANALYSIS-005` on owner mismatch instead of a generic 404).
- `cancelAnalysis` only accepts `UPLOADING` analysis, same restriction as `startUpload`, so a canceled analysis can never race a pipeline already in flight — by the time an analysis reaches `ANALYZING` its photos are the ones `startUpload` already locked in. On success it hard-closes the session (`FAILED`/`CANCELED` + all photos `FAILED`) rather than deleting rows, so the client's create-analysis flow can immediately retry (the partial unique index no longer blocks it) while the canceled session remains visible in history like any other failure. GCS cleanup is asynchronous and best-effort (see `AnalysisCleanupEventListener` above); nothing currently retries a failed `deleteByPrefix`, so a cancel can legitimately leave orphaned objects in storage on delete failure — same trade-off already accepted by `AnalysisWithdrawalService`. A future batch job to sweep and re-delete orphaned prefixes for `FAILED` analyses is not implemented; that gap is recorded here rather than as a comment in the listener.
- Analysis creation and upload verification require the authenticated principal (`UserId`). Foreign board and analysis identifiers return not found without exposing ownership.
- Board access goes through the port-free `BoardAccessService` only, never `BoardQueryService` or a board repository. `createAnalysis` takes the target board row lock (`getOwnedByIdForUpdate`) before the active-analysis pre-check, so it serializes against board deletion and a concurrent delete makes creation fail with `BOARD-002` instead of leaving an active analysis on a deleted board. That lookup is `MANDATORY`-propagation, so it may only be called from inside an already-open transaction.
- `AnalysisStatus.ACTIVE` (`UPLOADING`, `ANALYZING`) is the single definition of "in progress" shared by the active-analysis pre-check, active-analysis recovery, and the board deletion guard. Keep it aligned with the `uk_analysis_active` partial unique index predicate and the status transitions in `docs/api-spec/api-spec.md` and `docs/erd/schema.dbml`.
- Board deletion does not touch finished (`COMPLETED`/`FAILED`) analysis rows: the spec defines no deletion policy for analysis sessions, so the history stays and keeps pointing at the soft-deleted board.
- `startUpload` only accepts `UPLOADING` analysis. It checks photos currently `PENDING`; GCS objects with `size > 0` become `COMPLETED`, while missing or 0-byte objects become `FAILED` and are excluded from the pipeline. The analysis transitions to `ANALYZING`, so calling `startUpload` again returns `ANALYSIS-003` instead of acting as a no-op. The `UPLOADING` check runs **twice** through `Analysis.requireUploading()`: once on the unlocked read before the GCS listing, and again inside the transaction right after `findByIdForUpdate`, so a request that passed the first check while another `startUpload` was in flight still fails with `ANALYSIS-003` and marks nothing `COMPLETED`. If no pending photo has a non-empty object, nothing is written and the analysis stays `UPLOADING` with `ANALYSIS-008` (`NO_UPLOADED_PHOTOS`), so the client can upload and retry.
- `upload_status`/`status`/`content_type` are DB `VARCHAR`, not Postgres `ENUM`s — value-set validation lives only in the Kotlin enums; repositories map `String ↔ enum` at the boundary (`PhotoContentType.entries.find { it.mimeType == ... }` / `.mimeType`, same pattern as `UploadStatus.valueOf(...)` / `.name`).
- This domain owns the sticker domain's analysis/photo integration adapters (`infrastructure/integration/Sticker*`), following the same "provider side owns the adapter" rule as `BoardAnalysisActivityAdapter`. Sticker code never reads `analysis` or `photos` directly; every cross-domain read goes through `AnalysisQueryService` / `PhotoQueryService`.
- Ownership checks are fail-closed: a missing analysis, a user/board mismatch, or any photo id outside the analysis or not upload-completed returns `false`, and the sticker domain converts that into `STICKER-001`. The pipeline never trips the COMPLETED requirement because `startUpload` publishes only photos it just marked `COMPLETED`, and the recap read path fails fast (500) instead of silently dropping a non-completed photo a recap references.
- Recap photo reads require `photos.taken_at`; a null value is a data-integrity bug and fails with `IllegalStateException` (500) rather than being silently dropped.
- The paid/destructive external adapters of this domain (`PhotoStorage`, `ThemeClassifier`, `StickerGenerator`, `StickerStorage`) are replaced by `@Primary` fakes from `analysis/support/AnalysisTestConfig`, which the shared `support/IntegrationTest` base class imports for every integration test. No test opts in with its own `@Import`, so a new test cannot forget it and hit real GCS or Vertex AI. `FakePhotoStorage` deliberately delegates `issueReadUrls` to the real `GcsReadUrlIssuer`: read-URL signing is local RSA against the dummy test key with no network call and no cost, and keeping it real is what lets recap tests assert the exact signed object key.
- All four fakes are `ResettableFake`, and `support/IntegrationTest` truncates the DB and resets every one of them before each root `Given`. Never add a per-spec `beforeSpec`/`afterEach` reset — it is redundant and hides which leaf actually set the state.
- **`FakePhotoStorage.issueUploadUrls` must never register an uploaded object.** Signing a PUT URL does not create the object in GCS, so a fake that registers one makes `ANALYSIS-008` unreachable and every `startUpload` spec pass without a single upload. A spec that wants a photo present calls `markUploaded(photo)` / `markUploaded(photos)` (optionally `size = 0` for the empty-body case) and `markMissing(photo)` to take one away. The failure knobs are `issueUploadUrlsFailure` (pins "URL signing happens after the create transaction commits"), `deleteAllFailure` (pins the best-effort cancel cleanup), and `onUploadedObjects`, a hook that runs inside `startUpload` between the unlocked status check and the row lock — that is the seam the post-lock `ANALYSIS-003` test uses. `FakeStickerGenerator.onGenerate` (receives the `targetSubject`, so one theme can fail while others succeed) and `FakeStickerStorage.uploadFailure` drive the `ANALYSIS-011` paths on both sides: degraded to a null `stickerImageKey` in the pipeline, surfaced as 502 by `AnalysisStickerRegenerationAdapter`.
- The listener's "save stickers and `markCompleted` in one transaction" rule is pinned by adding a temporary `CHECK (status <> 'COMPLETED')` constraint on `analysis` around one `handle` call: `markCompleted` then fails after the stickers were written, and the spec asserts zero stickers survive. Do not replace that with a production seam — the constraint is created and dropped inside the one `When`.
- Photo objects and generated sticker objects share one bucket but not one key space: `PhotoObjectKeys` owns `photos/{analysisId}/...` and `StickerObjectKeys` owns `stickers/{analysisId}/...` for initial output plus `stickers/{stickerId}/{sourcePhotoId}-{regenerationId}.png` for regeneration output. Uploads (`GcsPhotoStorage`, `GcsStickerStorage`) live here; read URL signing for both is the shared `global/storage/GcsReadUrlIssuer`, reached through `PhotoStorage.issueReadUrls` for photos and through the sticker domain's `StickerImageStoragePort` for stickers.
- `AnalysisStickerResult.imageKey` must receive the bare object key from `StickerObjectKeys.keyFor(...)` or `StickerObjectKeys.keyForRegeneration(...)`, never a `gs://` URI — the latter would be signed as a literal object name and produce a broken read URL.
- **`UPLOADING` / `ANALYZING` 에 멈춘 분석은 만료 배치가 정리한다.** `uk_analysis_active` 가 사용자당 진행 중 분석을 1개로 강제하므로, 파이프라인이 죽거나 사용자가 업로드 도중 이탈해 남은 행은 그 사용자의 새 분석을 **영구히** 409 `ANALYSIS-002` 로 막는다. 프로덕션에서 26일째 막혀 있던 사용자 4명이 이 배치를 만든 이유이고, 4명 모두 성공한 분석이 0건이었다.
- 만료 기준은 `created_at` 이 아니라 **`updated_at`** 이다. `analysis_set_updated_at` 트리거가 모든 UPDATE 에서 `updated_at` 을 갱신하므로, 진행률이 오르고 있는 살아 있는 `ANALYZING` 은 계속 신선해지고 죽은 것만 오래된 상태로 남는다. `created_at` 을 쓰면 오래 걸리는 정상 분석까지 죽인다. 그래서 테스트에서 오래된 행을 만들려면 그 statement 동안만 트리거를 꺼야 한다 — `StaleAnalysisCleanupServiceTest.ageTo` 가 그 방법이다.
- 만료는 사용자 취소와 **같은 코드**를 쓴다 — `AnalysisDiscardService.discard(analysisId, reason)`. 두 경로가 절차를 각자 갖고 있으면 한쪽만 고쳐져 조용히 어긋난다. 달라지는 것은 `failedReason` 하나뿐이다. 이벤트 이름이 `AnalysisCanceledEvent` 에서 바뀐 것은 발행자가 둘(사용자 취소, 서버 만료)이 됐기 때문이다. 리스너가 하는 일은 어느 쪽이든 "끝내 못 쓴 분석의 업로드 오브젝트를 지운다" 하나다.
- 만료는 푸시를 보내지 않는다. 한 시간 넘게 방치된 분석의 실패 알림은 사용자가 이미 화면을 떠난 뒤에 도착하는 소음이고, 이 배치의 목적은 통보가 아니라 점유 해제다.
- 배치는 `ANALYSIS_STALE_CLEANUP_ENABLED` 로 켜고 끄며 **운영 기본값은 켜짐**이다(`.env.template`). 탈퇴 정리 배치와 달리 하드 삭제가 없고 상태만 `FAILED` 로 바꾸므로 되돌릴 수 없는 작업이 아니다. 테스트 프로파일에서는 꺼져 있어 스케줄러 빈이 뜨지 않는다 — 로직 검증은 `StaleAnalysisCleanupService` 를 직접 부르는 쪽에서 한다.
- Gemini response policy has exactly two grades, and `VertexAiGeminiClassifier` must not add a third. **Fail the analysis** (`INVALID_GEMINI_RESPONSE`, `ANALYSIS-007`): a blank `theme`/`recap.badge`/`recap.text`/`stickerTargetSubject`, an out-of-set or duplicated `stickerSourcePhotoId`, a photo id outside the request, and a theme count outside `MIN_THEME_COUNT..MAX_THEME_COUNT`. `classifyAndRecap` therefore calls `ThemeClassificationValidator.validate` unconditionally — it must never be guarded by `if (classifications.isNotEmpty())`, which would make `MIN_THEME_COUNT` unreachable and let a response with no usable theme finish as a `COMPLETED` analysis holding zero stickers. **Degrade silently** (log a warning, keep the analysis): only `mainColor` and `comments`, per the next rule.
- `AnalysisStickerResult.mainColor` / `ThemeAnalysisResult.stickerMainColor` comes from Gemini's classification response (`sticker.mainColor`). Unlike the fail-the-analysis fields above, a missing or malformed `mainColor` does not throw `INVALID_GEMINI_RESPONSE` and does not fail the whole analysis — `VertexAiGeminiClassifier.sanitizedMainColor` degrades it to a fixed default instead, since it is cosmetic (recap-screen background color) and not worth discarding an otherwise-valid analysis over. `regenerateSticker()` applies the same sanitization, so `POST /stickers/{stickerId}/regenerate` also refreshes `stickers.main_color` alongside the image.
- `ThemeAnalysisResult.text` is the prompt's "한 문장의 리캡 문구" and fills `AnalysisStickerResult.summary` (the recap's `한 줄 요약`), not a recap comment. It used to be saved as the single non-floating comment, but that "하단 순차 노출 문장형" UI was removed. `Sticker.MAX_SUMMARY_LENGTH` is 100, well above what a single sentence yields, so keep the prompt's length wording in sync if either side changes.
- `ThemeClassification.comments` / `ThemeAnalysisResult.comments` (`analysis/domain/ThemeComment.kt`: `content`, `posX`, `posY`) come from the same Gemini call as `recap`/`sticker`, requested as two separate arrays (`comments.speechBubbles` with required `posX`/`posY`, `comments.keywordChips` as bare strings) so the structured-output schema can't produce a half-filled coordinate pair — `VertexAiGeminiClassifier.sanitizedComments` then flattens both into `List<ThemeComment>`, dropping any speech bubble missing content or a coordinate and any blank keyword chip (same graceful-degradation pattern as `sanitizedMainColor`; a bad/empty `comments` response never fails the whole classification). `AnalysisPipelineEventListener.toStickerResult()` maps each `ThemeComment` 1:1 into a `RecapCommentCreation` (`posX`/`posY` both null for a keyword chip, both set for a speech bubble), matching `RecapComment`'s all-or-nothing position rule.
- Infrastructure adapters in this domain raise no domain exception. `GcsSourcePhotoImageReader`, `PixianBackgroundRemover` and `StickerImageCropper` let `StorageException`, `RestClientException`/`RestClientResponseException` and `IOException` propagate; the application layer decides policy and maps them to `ANALYSIS-011` — in `AnalysisPipelineService.generateAndUploadSticker` for the pipeline (degraded to a null sticker through `PipelineRun.degrade`, which logs it) and in `AnalysisStickerRegenerationAdapter` for `POST /stickers/{stickerId}/regenerate` (surfaced to the client). The regeneration adapter is the provider side of a sticker port, so owning that mapping is the analysis domain deciding its own contract, not an outbound adapter leaking one.
- Withdrawn-user cleanup deletes stored objects before rows, so a failure after object deletion leaves rows that the next batch run retries; deleting rows first would leak objects nothing can find again. It is the only path that hard-deletes analysis and photo rows.
- **Service bodies in `application/` carry no logging, timing, best-effort swallowing, or retry.** Pipeline steps go through the `PipelineRun` recorder (`measured` / `degrade` / `measuredGeminiCall`), side effects that must not fail the caller go through `global/logging`'s `bestEffort(log, "…") { }`, and retry goes through `global/retry`'s `retrying(...)`. `grep -n "log\\.\\|nanoTime\\|elapsedMs\\|runCatching" application/*Service*.kt application/*Listener*.kt` must stay empty — `PipelineRun.kt` is the one file in this package allowed to hold them. No `@Aspect` for the pipeline: its timed units are internal steps inside one method, not bean method boundaries, so a proxy cannot see them (CLAUDE.md 2.2).
- **Request-shape validation belongs to the command types, not to `AnalysisService`.** A new group/count rule is an `init` check on `CreateAnalysisCommand` or `PhotoUploadGroupRequest`; a new analysis-state rule is a method on `Analysis` next to `requireUploading()`. Because the rules fire in the constructor, a test that asserts `ANALYSIS-001`/`ANALYSIS-009`/`ANALYSIS-010` must build the command **inside** `shouldThrow`, not in the `Given` block.
- The old `images` table / `image` domain (file-name-based, per-image signed URL issuance and client-reported upload completion) was fully replaced by this domain in the same change — see git history if you need the old shape.
