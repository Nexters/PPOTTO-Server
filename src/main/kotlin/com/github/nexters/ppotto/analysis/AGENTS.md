# analysis

Analysis domain. Owns both `Analysis` and `Photo` — a photo only ever exists as part of an analysis (`Analysis : Photo = 1:N` via `photos.analysis_id`), so they share one domain package instead of being split into `analysis`/`photo`. No DB-level FK constraints (same reasoning as `board/`). The 90–100 photo count validation is implemented via service-level validation in `AnalysisService.createAnalysis` (returns 400 `ANALYSIS-001`). The one-active-analysis-per-user limit is enforced via service-level pre-check and a partial unique index `uk_analysis_active` on `analysis(user_id) WHERE status IN (UPLOADING, ANALYZING, GENERATING)` (returns 409 `ANALYSIS-002`). Daily quota is intentionally not implemented yet — see Rules below.

|-----------|---------|
| `domain/Analysis.kt` | Pure Kotlin model: `id`, `userId`, `boardId`, `status`, `progress`, `failedReason`, `startedAt`, `completedAt`, `createdAt`, `updatedAt` |
| `domain/AnalysisStatus.kt` | `UPLOADING` / `ANALYZING` / `GENERATING` / `COMPLETED` / `FAILED` — pure Kotlin enum, not the jOOQ-generated type. `companion object ACTIVE` defines the set of active states (`UPLOADING`, `ANALYZING`, `GENERATING`) used in service-level validation and DB partial unique index. |
| `domain/Photo.kt` | Pure Kotlin model: `id`, `analysisId`, `boardId`, `contentType: PhotoContentType`, `uploadStatus`, `uploadedAt`, `takenAt`, `createdAt`, `updatedAt` |
| `domain/UploadStatus.kt` | `PENDING` / `COMPLETED` / `FAILED` |
| `domain/PhotoContentType.kt` | `JPEG`/`PNG`/`HEIC` enum, each carrying `mimeType` (`"image/jpeg"` etc., stored in `photos.content_type` and sent to GCS as the `Content-Type` header) and `extension` (`"jpg"` etc., used for the object key). This is the single source of truth for which content types are accepted. `fromMimeType(String)` throws `InvalidInputException` (→ 400 `COMMON-001` via `GlobalExceptionHandler`'s `BusinessException` handler) for an unsupported value. Callers must pass a non-null string; the request DTO field is required (bean-validation `@NotBlank`) and validation happens at both the DTO boundary and in the service. |
| `domain/PhotoStorage.kt` | Port interface: `issueUploadUrls(targets): List<String>` (batch, same order as input), `existingObjects(prefix): Map<String, BlobMeta>` (`BlobMeta(size, createdAt)` — carries the GCS object's real size/creation time so the caller doesn't have to re-derive `uploaded_at` or trust bare key existence). No Spring/GCS SDK imports — the adapter is `infrastructure/GcsPhotoStorage.kt` |
| `domain/AnalysisErrorCode.kt` | `PHOTO_COUNT_OUT_OF_RANGE` (`ANALYSIS-001`, 400) — thrown by `createAnalysis` if `photos.size !in 90..100`. `ACTIVE_ANALYSIS_EXISTS` (`ANALYSIS-002`, 409) — thrown by `createAnalysis` if the user already has an active analysis (UPLOADING/ANALYZING/GENERATING), caught both at service pre-check and as a DB unique constraint violation fallback. `ALREADY_STARTED_OR_FINISHED` (`ANALYSIS-003`, 409) — thrown by `startUpload` when `analysis.status != UPLOADING` |
| `infrastructure/PhotoObjectKeys.kt` | `object` (stateless, no DI needed) wrapping the shared `global/storage/ObjectKeyGenerator` with this domain's own convention: namespace `"photos"`, prefix `photos/{analysisId}/`, key `photos/{analysisId}/{photoId}.{PhotoContentType.extension}`. The `analysisId` segment lets `GcsPhotoStorage.existingObjects(prefix)` list all of one analysis's objects in a single GCS call. Originally lived in `domain/` as a `@Component`, which violated this domain's "no Spring imports" rule — moved here and converted to a plain `object` since it has no state to inject |
| `infrastructure/AnalysisRepository.kt` | DSLContext-based persistence: create and lock lookup plus active-analysis checks scoped by user or board owner |
| `infrastructure/integration/BoardAnalysisActivityAdapter.kt` | Production `BoardAnalysisActivityPort` adapter through `AnalysisQueryService` |
| `infrastructure/PhotoRepository.kt` | `saveAll(analysisId, boardId, items)` — single multi-row `INSERT ... RETURNING`, relies on Postgres preserving input order for plain multi-VALUES inserts so the response can zip photos back to the request order. `findPendingByAnalysisId()`, `findAllByAnalysisId()`, `markCompletedBatch(updates)`, and `markFailedBatch(ids)` support upload verification. Completed photos store the GCS object's real creation time in `uploaded_at`; missing or 0-byte pending photos are marked `FAILED` when analysis starts. `toDomain()`'s DB value mapping: `content_type` is mapped via `PhotoContentType.entries.find + error(...)` (not `fromMimeType`, which is for request validation and throws 400) — DB inconsistency is a server problem (500), not client input error (400) |
| `infrastructure/GcsPhotoStorage.kt` | GCS SDK implementation of `PhotoStorage`. `issueUploadUrls` loops internally (GCS V4 signing has no batch API) but is called once per request from the service; each signed URL also signs `x-goog-content-length-range: 0,{MAX_PHOTO_SIZE_BYTES}` (15MB, per spec) as an ext header, so GCS rejects oversized PUT bodies with 400 — the client must send the identical header value or GCS returns 403 `SignatureDoesNotMatch` instead, and a web client additionally needs this header allow-listed in the bucket's CORS config (both are tracked outside this repo, not yet done). `existingObjects` uses `Storage.list(bucket, prefix(...))` — one GCS call instead of one `get()` per photo — and maps each `Blob` to `BlobMeta(size, createTimeOffsetDateTime)` instead of discarding everything but the name |
| `infrastructure/VertexAiGeminiClassifier.kt` | Gemini classification adapter. Groups photos into themes and chooses each theme's sticker source photo/subject with visual appeal criteria such as clarity, lighting, composition, expressive subject, and clean cutout potential |
| `infrastructure/VertexAiStickerGenerator.kt` | Gemini image generation adapter for natural sticker cutouts. Prompts for PNG output with a fully transparent alpha background, polished subject edges, preserved original appeal, and no replacement background, border, shadow, decoration, or over-stylization |
| `application/AnalysisService.kt` | Authenticated create and upload-verification/start use cases; enforces row-locked board ownership and analysis ownership before persistence or storage access. `startUpload` completes uploaded pending photos, marks missing or 0-byte pending photos as `FAILED`, transitions the analysis to `ANALYZING`, and publishes `AnalysisStartRequestedEvent`; the pipeline listener marks it `COMPLETED` or `FAILED` after processing. |
| `application/AnalysisQueryService.kt` | Read-only active-analysis application boundary used by cross-domain adapters |
| `application/AnalysisResults.kt` | Result types returned by the service (kept separate from the presentation dto): `AnalysisCreationResult`, `PhotoUploadUrlItem`, `PhotoUploadItemRequest` (`contentType: String` — required, validated by service), `UploadVerificationResult` |
| `presentation/AnalysisController.kt` | Authenticated `POST /analysis` and `POST /analysis/{analysisId}/start` v1 endpoints |

## Rules

- This tracks the client's real OpenAPI spec (`analysis` tag) for `POST /analysis` and `POST /analysis/{analysisId}/start` only. Implemented: the 90–100 photo count check (`ANALYSIS-001`, service-level validation returning 400), the one-active-analysis-per-user limit (`ANALYSIS-002`, service pre-check + partial unique index `uk_analysis_active` returning 409 on violation), already-started/finished conflict (`ANALYSIS-003`, 409), and AI pipeline start from `start`. Not implemented yet: `GET /analysis/active`, `GET /analysis/{id}`, `DELETE /analysis/{id}`, `POST /analysis/{id}/reissue`, and the daily quota (out of scope for this PR — to be implemented later). Not-found cases use `NotFoundException(ANALYSIS-005)` for missing analysis and generic not found for ownership mismatch.
- Analysis creation and upload verification require the authenticated UUID principal. Foreign board and analysis identifiers return not found without exposing ownership.
- Board access goes through the port-free `BoardAccessService` only, never `BoardQueryService` or a board repository. `createAnalysis` takes the target board row lock (`getOwnedByIdForUpdate`) before the active-analysis pre-check, so it serializes against board deletion and a concurrent delete makes creation fail with `BOARD-002` instead of leaving an active analysis on a deleted board. That lookup is `MANDATORY`-propagation, so it may only be called from inside an already-open transaction.
- `AnalysisStatus.ACTIVE` (`UPLOADING`, `ANALYZING`) is the single definition of "in progress" shared by the active-analysis pre-check and the board deletion guard. The `uk_analysis_active` partial unique index predicate still also lists `GENERATING`, which the enum no longer declares — harmless (no row can hold a value the enum cannot produce), but keep both aligned with the status transitions in `docs/api-spec/api-spec.md` and `docs/erd/schema.dbml`.
- Board deletion does not touch finished (`COMPLETED`/`FAILED`) analysis rows: the spec defines no deletion policy for analysis sessions, so the history stays and keeps pointing at the soft-deleted board.
- `startUpload` only accepts `UPLOADING` analysis. It checks photos currently `PENDING`; GCS objects with `size > 0` become `COMPLETED`, while missing or 0-byte objects become `FAILED` and are excluded from the pipeline. The analysis transitions to `ANALYZING`, so calling `startUpload` again returns `ANALYSIS-003` instead of acting as a no-op.
- `upload_status`/`status`/`content_type` are DB `VARCHAR`, not Postgres `ENUM`s — value-set validation lives only in the Kotlin enums; repositories map `String ↔ enum` at the boundary (`PhotoContentType.fromMimeType(...)` / `.mimeType`, same pattern as `UploadStatus.valueOf(...)` / `.name`).
- Any new test that invokes `AnalysisService` must `@Import` `analysis/support/AnalysisTestConfig` so the `@Primary` fake (`FakePhotoStorage`) replaces the real GCS adapter, same mechanism the former `image` domain used.
- The old `images` table / `image` domain (file-name-based, per-image signed URL issuance and client-reported upload completion) was fully replaced by this domain in the same change — see git history if you need the old shape.
