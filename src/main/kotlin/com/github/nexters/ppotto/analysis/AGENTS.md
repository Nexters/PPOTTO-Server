# analysis

Analysis domain. Owns both `Analysis` and `Photo` — a photo only ever exists as part of an analysis (`Analysis : Photo = 1:N` via `photos.analysis_id`), so they share one domain package instead of being split into `analysis`/`photo`. No DB-level FK constraints (same reasoning as `board/`). The 20–100 photo group count validation (each group 1–10 photos, `MIN_GROUP_COUNT`/`MAX_GROUP_COUNT`/`MAX_BURST_GROUP_SIZE`) is implemented in the `init` of `CreateAnalysisCommand` and `PhotoUploadGroupRequest` (returns 400 `ANALYSIS-001`/`ANALYSIS-010`/`ANALYSIS-009`), so an invalid request never reaches `AnalysisService`. The one-active-analysis-per-user limit is enforced via service-level pre-check and a partial unique index `uk_analysis_active` on `analysis(user_id) WHERE status IN (UPLOADING, ANALYZING)` (returns 409 `ANALYSIS-002`). The pre-check is deliberately kept on top of the constraint: it runs inside the board row lock that `createAnalysis` already holds, so the common case answers 409 without burning an insert and a rolled-back transaction, while the constraint stays as the race-proof fallback. Daily quota is intentionally not implemented yet — see Rules below.

## Rules

- Typed identifiers (`AnalysisId`, `PhotoId`, `BoardId`, `UserId`) run end to end through this package: controller, DTOs, application services, `Analysis`/`Photo` models, the `PhotoStorage`/`ThemeClassifier` ports, the `integration/` adapters, and the public signatures of `AnalysisRepository`/`PhotoRepository`. jOOQ id columns are generated typed (codegen `forcedType`), so DSL bindings and `toDomain` take and return typed ids directly — there is no wrap/unwrap layer left in this domain. Raw `UUID` remains only where it is not an entity id: `photos.burst_group_id` (an internal grouping token that crosses no domain boundary) and the sticker regeneration id.
- This tracks the client's real OpenAPI spec (`analysis` tag). Implemented: the 20–100 photo group count check, each group 1–10 photos (`ANALYSIS-001`, enforced in `CreateAnalysisCommand.init`, returning 400), the one-active-analysis-per-user limit (`ANALYSIS-002`, service pre-check + partial unique index `uk_analysis_active` returning 409 on violation), already-started/finished conflict (`ANALYSIS-003`, 409), the `UPLOADING`-only cancel (`ANALYSIS-004`, 409, `DELETE /analysis/{id}`), active-analysis recovery, analysis status polling, upload URL reissue (`POST /analysis/{id}/reissue`), and AI pipeline start from `start`. Not implemented yet: the daily quota (out of scope for this PR — to be implemented later). Not-found cases use `NotFoundException(ANALYSIS-005)` for missing analysis and ownership mismatch in query APIs, including `cancelAnalysis` and `startUpload`/`reissueUploadUrls` (both share `findOwnedAnalysis`, which consistently throws `ANALYSIS-005` on owner mismatch instead of a generic 404).
- `cancelAnalysis` only accepts `UPLOADING` analysis, same restriction as `startUpload`, so a canceled analysis can never race a pipeline already in flight — by the time an analysis reaches `ANALYZING` its photos are the ones `startUpload` already locked in. On success it hard-closes the session (`FAILED`/`ANALYSIS-016`/`CANCELED` + all photos `FAILED`) rather than deleting rows, so the client's create-analysis flow can immediately retry (the partial unique index no longer blocks it) while the canceled session remains visible in history like any other failure. GCS cleanup is asynchronous and best-effort (see `AnalysisCleanupEventListener` above); nothing currently retries a failed `deleteByPrefix`, so a cancel can legitimately leave orphaned objects in storage on delete failure — same trade-off already accepted by `AnalysisWithdrawalService`. A future batch job to sweep and re-delete orphaned prefixes for `FAILED` analyses is not implemented; that gap is recorded here rather than as a comment in the listener.
- Analysis creation and upload verification require the authenticated principal (`UserId`). Foreign board and analysis identifiers return not found without exposing ownership.
- Board access goes through the port-free `BoardAccessService` only, never `BoardQueryService` or a board repository. `createAnalysis` takes the target board row lock (`getOwnedByIdForUpdate`) before the active-analysis pre-check, so it serializes against board deletion and a concurrent delete makes creation fail with `BOARD-002` instead of leaving an active analysis on a deleted board. That lookup is `MANDATORY`-propagation, so it may only be called from inside an already-open transaction.
- `AnalysisStatus.ACTIVE` (`UPLOADING`, `ANALYZING`) is the single definition of "in progress" shared by the active-analysis pre-check, active-analysis recovery, and the board deletion guard. Keep it aligned with the `uk_analysis_active` partial unique index predicate and the status transitions in `docs/api-spec/api-spec.md` and `docs/erd/schema.dbml`.
- Board deletion does not touch finished (`COMPLETED`/`FAILED`) analysis rows: the spec defines no deletion policy for analysis sessions, so the history stays and keeps pointing at the soft-deleted board.
- `startUpload` only accepts `UPLOADING` analysis. It checks photos currently `PENDING`; GCS objects with `size > 0` become `COMPLETED`, while missing or 0-byte objects become `FAILED` and are excluded from the pipeline. The analysis transitions to `ANALYZING`, so calling `startUpload` again returns `ANALYSIS-003` instead of acting as a no-op. The `UPLOADING` check runs **twice** through `Analysis.requireUploading()`: once on the unlocked read before the GCS listing, and again inside the transaction right after `findByIdForUpdate`, so a request that passed the first check while another `startUpload` was in flight still fails with `ANALYSIS-003` and marks nothing `COMPLETED`. If no pending photo has a non-empty object, nothing is written and the analysis stays `UPLOADING` with `ANALYSIS-008` (`NO_UPLOADED_PHOTOS`), so the client can upload and retry.
- `upload_status`/`status`/`content_type` are DB `VARCHAR`, not Postgres `ENUM`s — value-set validation lives only in the Kotlin enums; repositories map `String ↔ enum` at the boundary (`PhotoContentType.entries.find { it.mimeType == ... }` / `.mimeType`, same pattern as `UploadStatus.valueOf(...)` / `.name`).
- This domain owns the sticker domain's analysis/photo integration adapters (`infrastructure/integration/Sticker*`), following the same "provider side owns the adapter" rule as `BoardAnalysisActivityAdapter`. Sticker code never reads `analysis` or `photos` directly; every cross-domain read goes through `AnalysisQueryService` / `PhotoQueryService`.
- Ownership checks are fail-closed: a missing analysis, a user/board mismatch, or any photo id outside the analysis or not upload-completed returns `false`, and the sticker domain converts that into `STICKER-001`. The pipeline never trips the COMPLETED requirement because `startUpload` publishes only photos it just marked `COMPLETED`, and the recap read path fails fast (500) instead of silently dropping a non-completed photo a recap references.
- Recap photo reads require `photos.taken_at`; a null value is a data-integrity bug and fails with `IllegalStateException` (500) rather than being silently dropped.
- The paid/destructive external adapters of this domain (`PhotoStorage`, `ThemeClassifier`, `StickerGenerator`, `StickerStorage`) are replaced by `@Primary` fakes from `analysis/support/AnalysisTestConfig`, which the shared `support/IntegrationTest` base class imports for every integration test. No test opts in with its own `@Import`, so a new test cannot forget it and hit real GCS or Vertex AI. `FakePhotoStorage` deliberately delegates `issueReadUrls` to the real `GcsReadUrlIssuer`: read-URL signing is local RSA against the dummy test key with no network call and no cost, and keeping it real is what lets recap tests assert the exact signed object key.
- All four fakes are `ResettableFake`, and `support/IntegrationTest` truncates the DB and resets every one of them before each root `Given`. Never add a per-spec `beforeSpec`/`afterEach` reset — it is redundant and hides which leaf actually set the state.
- **`FakePhotoStorage.issueUploadUrls` must never register an uploaded object.** Signing a PUT URL does not create the object in GCS, so a fake that registers one makes `ANALYSIS-008` unreachable and every `startUpload` spec pass without a single upload. A spec that wants a photo present calls `markUploaded(photo)` / `markUploaded(photos)` (optionally `size = 0` for the empty-body case) and `markMissing(photo)` to take one away. The failure knobs are `issueUploadUrlsFailure` (pins "URL signing happens after the create transaction commits"), `deleteAllFailure` (pins the best-effort cancel cleanup), and `onUploadedObjects`, a hook that runs inside `startUpload` between the unlocked status check and the row lock — that is the seam the post-lock `ANALYSIS-003` test uses. `FakeStickerGenerator.onGenerate` (receives the `targetSubject`, so one theme can fail while others succeed) and `FakeStickerStorage.uploadFailure` 는 초기 파이프라인의 테마별 실패·전체 실패(`013`)와 재생성 API의 `011`을 검증한다.
- The listener's "save stickers and `markCompleted` in one transaction" rule is pinned by adding a temporary `CHECK (status <> 'COMPLETED')` constraint on `analysis` around one `handle` call: `markCompleted` then fails after the stickers were written, and the spec asserts zero stickers survive. Do not replace that with a production seam — the constraint is created and dropped inside the one `When`.
- Photo objects and generated sticker objects share one bucket but not one key space: `PhotoObjectKeys` owns `photos/{analysisId}/...` and `StickerObjectKeys` owns `stickers/{analysisId}/...` for initial output plus `stickers/{stickerId}/{sourcePhotoId}-{regenerationId}.png` for regeneration output. **이미지 해상도는 호출마다 다르고, `GeminiPrompt` 가 그것을 들고 다닌다.** 분류만 `MEDIA_RESOLUTION_MEDIUM` 이고 재생성·재확인은 지정하지 않는다(모델 기본값). 측정 근거: 사진 82장 기준 기본값 92,921 토큰 / MEDIUM 48,401 / LOW 26,216 인데, **토큰을 두 배 써도 두 배 잘 보지 않았다** — MEDIUM 이 기본값보다 `observedDetails` 를 더 조밀하게(테마당 5.0개 대 4.0개) 뽑았고 비용은 절반이었다. LOW 로 더 내리면 읽어야 아는 것들(간판 번호, 잡지 제호, 포스터 문구)이 사라져 카피의 구체성이 죽는다. 재생성·재확인에 해상도를 내리지 않는 이유는 사진이 1장이라 토큰 부담이 없고, 컷아웃 대상을 고르는 판단에는 세밀함이 필요하기 때문이다 — `GeminiPromptTest` 가 이 둘을 모두 단언한다. 해상도를 바꾸면 429 압력도 같이 바뀐다(토큰이 곧 공용 풀 점유량이다).

**프롬프트는 이름 있는 섹션의 조립이고, 프롬프트 하나가 파일 하나다.** `GeminiPrompt.kt`가 `PromptSection`·`GeminiPrompt`·`geminiPrompt {}`를 들고, `ThemeClassificationPrompt.kt`/`StickerRegenerationPrompt.kt`/`StickerSubjectVerificationPrompt.kt`가 각자 자기 섹션을 선언하며, 여러 프롬프트가 공유하는 것만 `SharedPromptSections.kt`에 둔다(컷아웃 가이드·카피 예시·출력 언어·`COPY_VOICE`). **섹션 순서가 곧 프롬프트 순서**이므로 `section(...)` 호출 순서를 옮기면 모델이 읽는 순서가 바뀐다 — 카피 예시가 컷아웃 가이드 뒤에 오는 이유가 그것이고, 테스트가 그 인접성을 단언한다. `systemInstruction`은 `GeminiPrompt`가 들고 다니므로 분류 프롬프트만 톤을 갖는다는 규칙이 문서가 아니라 타입으로 강제된다 — 재생성·재확인 프롬프트에 톤을 붙이려면 그 함수를 고쳐야 한다.

**도메인 제약 숫자는 도메인 타입이 소유하고 에러 메시지가 보간한다.** `Analysis.MIN_PHOTO_GROUP_COUNT`/`MAX_PHOTO_GROUP_COUNT` 와 `Photo.MAX_BURST_GROUP_SIZE` 가 원본이고 `AnalysisErrorCode` 가 그것을 보간한다 — 상한을 바꿨을 때 사용자가 옛 숫자를 읽는 일이 없어야 한다. 이 상수들은 검증을 실행하는 `application/model/AnalysisResults.kt` 의 command 타입에 있었는데, 도메인은 application 을 참조할 수 없어 enum 이 보간할 수 없었다. DTO 는 이 상수를 참조하지 않는다(아래 규칙 참조).

**패키지 배치 규칙.** 도메인 루트는 `domain` / `application` / `infrastructure` / `presentation` 네 개뿐이다. 설정 클래스는 5번째 루트 폴더를 만들지 않고 `infrastructure/config/`에 둔다 — 외부 기술 설정은 어차피 인프라 관심사이고, 예전에는 같은 `@ConfigurationProperties`가 `config/`와 `infrastructure/`에 나뉘어 있었다. 아웃바운드 포트는 `application/port/`에 둔다(도메인이 아니다) — 안쪽이 포트를 소유하고, 다른 도메인들이 이미 그 자리를 쓴다. 서비스가 아닌 command·result 타입은 `application/model/`에 모아 `application` 바로 아래에는 서비스만 남긴다. `application` 바로 아래에는 서비스와 리스너만 둔다. 파이프라인은 서비스 하나가 아니라 실행 엔진이라 `application/pipeline/`으로 묶었다 — 실행 서비스, 이벤트 리스너, 계측 레코더(`PipelineRun`), 진행률 시뮬레이터가 한 덩어리로 움직인다. `infrastructure`는 외부 기술별로 갈린다: `gemini` / `pixian` / `storage` / `persistence` / `scheduling` / `image` / `config` / `integration`. 루트에 파일을 직접 두지 말 것.
