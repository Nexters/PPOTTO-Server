# Tests

Kotest BehaviorSpec (Given-When-Then) on JUnit Platform, with Testcontainers for integration tests.

| File | Description |

## Rules

- Integration tests extend `IntegrationTest` and use constructor injection:

```kotlin
class PhotoServiceTest(
    service: PhotoService,
) : IntegrationTest({
    Given("사진이 등록된 상태에서") {
        When("아이디로 조회하면") {
            Then("사진 정보를 반환한다") { ... }
        }
    }
})
```

- Test names in Korean. Use capitalized `Given`/`When`/`Then` (lowercase `when` needs backticks).
- Pure unit tests extend any Kotest spec directly without Spring.
- One Spring context (and one Postgres container) is shared across all integration tests via context caching. What splits the cache is the **set of imported configurations**, not the number of specs, so every shared fake belongs on `IntegrationTest` itself: `ObjectStorageTestConfiguration`, `AnalysisTestConfig` (GCS photo/sticker storage, Gemini, Pixian), `NotificationTestConfig` (FCM), and `UserTestConfig` (Apple/Kakao revoke, Redis session revoke) are imported there and must not be moved back to individual specs.
- A per-spec `@Import` is for a fake that only that spec's scenario needs — an internal-port or domain-adapter stub (`BoardTestConfig`, `AuthTestConfig`, `UserJourneyTestConfig`) or a one-off blocking/failing double for a concurrency or rollback test. Each distinct import set is another context and another Postgres container, so adding one is a deliberate cost, not a default.
- A fake that stands in for paid, external, or destructive work (GCS, Gemini, Pixian, FCM, Apple/Kakao revoke) is promoted onto `IntegrationTest`, so forgetting an import can never hit the real service (CLAUDE.md 6.3). A spec that needs to observe such a path asserts on the fake (`FakePhotoStorage.deletedPrefixes`, `FakePushNotifier.sentMessages`, `FakeSocialAccountRevoker.revocations`), never through the production adapter.
- **The shared fakes are programmable, not always-successful.** Set the knob in the `Given`, and `IntegrationTest` clears it before the next leaf:
  - `FakePhotoStorage`: `issueUploadUrlsFailure`, `deleteAllFailure`.
  - `FakePushNotifier`: `invalidTokens`, `failedTokens` (per-token results) and `failure` (the whole call throws).
  - `FakeSocialAccountRevoker`: `failure`.
- **`FakePhotoStorage.issueUploadUrls` does not upload.** It only hands back a URL, exactly like the real signed-URL flow. A photo counts as uploaded only after `markUploaded(photo)` / `markUploaded(photos)`, so any spec that starts an analysis must mark its photos first or `POST /analysis/{id}/start` answers `ANALYSIS-008`. That asymmetry is the point: it is what makes the no-uploaded-photos path testable at all.
- **A `@Component`/`@Service`/`@RestController` declared in the test sources is component-scanned into *every* `@SpringBootTest` context, not just the spec that needs it.** `AdvisoryLockProbeService` is the deliberate case: it exists only to carry `@AdvisoryLock` annotations, holds no state, touches nothing on construction, and is named so it is obvious where it came from when it shows up in a bean list. Anything heavier — a bean that writes, schedules, or registers itself with a shared registry — must be `@Profile`-gated instead (`ThrowingTestController` carries `@Profile("standalone-only")` for exactly this reason, because a `@RestController` in test sources otherwise appears in `OpenApiExampleWiringTest`).
- Avoid `@MockkBean`-style context mutations unless necessary; they evict the cached context outright.
- `IntegrationTest` uses `IsolationMode.InstancePerLeaf` while the Spring context stays cached, so stateful test doubles (latches, counters) must be resettable and reset per test. One-shot singleton fields silently stop blocking once a spec gains a second leaf. Implement `ResettableFake` on any shared fake and `IntegrationTest` resets it per leaf for free; a spec-local double (a blocking or failing one-off) still resets itself in `beforeTest`.
- **`InstancePerLeaf` re-runs only a leaf's ancestors, never its preceding siblings.** A spec whose stages depend on the previous stage (the user journey) must therefore override `isolationMode()` to `SingleInstance` and hold the carried state in the root `Given`. Do not fake it by nesting every stage inside the previous one — that re-runs the whole journey once per leaf.
- **Do not reach for `eventually` or `Thread.sleep`.** In the `test` profile every `AsyncConfig` executor is a `SyncTaskExecutor` and `AnalysisPipelineService` joins its own virtual-thread executor with `use`, so the analysis pipeline is finished by the time the HTTP call returns; a retry loop there only hides the regression where an executor is declared `!test`-only. The one genuinely asynchronous producer in this repo is Sentry's own transport in `SentryHttpPayloadEndToEndTest`, and even that waits on an explicit condition variable rather than polling. `eventually` would be defensible only there, and nowhere else.
- `@Primary` only overrides single-bean injection. For a port injected as `List<Port>` and resolved with `singleOrNull()` (all `sticker/application/port` contracts), registering a fake adds a second bean and breaks the service — test the production adapter instead.
- GCS signing needs no network: `src/test/resources/dummy-gcs-key.json` is a real RSA key, so read/upload V4 signed URLs are asserted against `https://storage.googleapis.com/ppotto-test-bucket/...` with real signatures. `AnalysisTestConfig` is on `IntegrationTest`, so photo upload/read URLs and photo prefix deletes go to `FakePhotoStorage`; the real V4 signing is still exercised by `GcsReadUrlIssuerTest` and by sticker image URLs, which go through the real `GcsStickerImageStorage` → `GcsReadUrlIssuer` path.
- Object deletion never reaches GCS either: `IntegrationTest` always imports `support/ObjectStorageTestConfiguration`, whose `@Primary` `RecordingObjectStorageCleaner` replaces `GcsObjectStorageCleaner` for every context. Do not remove that import when adding a test that triggers withdrawal cleanup.
- `UserJourneyIntegrationTest` authenticates through the real `BearerTokenAuthenticationFilter` with the JWT returned by `POST /auth/login`, so it exercises the HTTP layer instead of injecting a principal. The filter's servlet auto-registration is disabled; in the test profile it runs because the permit-all fallback chain in `auth/config/AuthSecurityConfig.kt` adds it explicitly. Analysis start goes through MockMvc and the test follows the pipeline-saved sticker result instead of calling `AnalysisResultSaveService` directly.

## AnalysisTestConfig and UserTestConfig were demoted once (2026-09-09) and re-promoted the same day

The first promotion broke two specs and was reverted. Both causes were removed later that day, so the promotion stands; if it breaks a spec again, fix where that spec observes the behaviour, do not demote the config.

- `UserTestConfig` used to register `FakeWithdrawnUserDataDeletionPort`, a `@Primary` override of the production composite adapter, so cross-domain cleanup stopped running everywhere (`fk_term_agreements_user` on `UserRepository.hardDelete`). The composite port, adapter, and fake were deleted; `WithdrawnUserCleanupService` now takes the four sub-ports directly and `UserTestConfig` only fakes the external revokers.
- `AnalysisTestConfig` registers `FakePhotoStorage`, so photo prefix deletes no longer reach `RecordingObjectStorageCleaner` through `GcsPhotoStorage`. The specs that asserted `deletedPrefixes shouldContain PhotoObjectKeys.prefixFor(...)` on the cleaner now assert on `FakePhotoStorage.deletedPrefixes`, and read-URL assertions check the object key inside the fake URL instead of a real signature.
